# build — Notes for AI Agents

This package holds the builders that wrap model objects for HTML templates, and the execute side of every pipeline step. [README.md](README.md) covers the architecture and the Widget save-pipeline mechanism; [model/step](../model/step/README.md) is the parse side, with every step documented in [STEPS.md](../model/step/STEPS.md).

- **Every pipeline step exists twice and is registered twice.** The parse side lives in [model/step](../model/step/) (a struct plus a `New…()` constructor, registered in the `do:` switch in [step.go](../model/step/step.go)); the execute side lives here (a `Step{Name}` struct with `Get`/`Post`, registered in the switch in [step_.go](step_.go)). Adding or renaming a step means touching all four places.
- **Build-side step structs must stay field-for-field identical to their model/step twins.** `ExecutableStep` converts with a plain type conversion (`StepSave(s)`), which only compiles while the two structs share the same fields in the same order. This is why [step_ProcessContent.go](step_ProcessContent.go) keeps its deprecated `AddTags`/`TagPath` fields — they exist purely to keep the conversion legal, so do not "clean them up".
- **A missing `ExecutableStep` case fails at request time, not compile time.** An unmatched step type falls through to [StepError](step_Error.go), which halts every pipeline that uses it with "Unrecognized Pipeline Step". After adding a model/step case, verify the build-side case exists too — nothing else will catch the omission.
- **File and type names drift from the `do:` name.** `do: "edit-table"` parses to `step.TableEditor` and executes as `StepTableEditor` in [step_EditTable.go](step_EditTable.go); `do: "promote-draft"` executes as `StepStreamPromoteDraft` in [step_PromoteDraft.go](step_PromoteDraft.go). When hunting a step, search the two registration switches, not the filenames.
- **Returning `nil` from a step's `Get`/`Post` means Continue.** The pipeline loop skips nil behaviors, so `nil` and `Continue()` are interchangeable — many steps use `nil` for their no-op verb. When chaining modifiers, start from `Continue()` or `Halt()`: `WithContentType` is the one modifier in [pipeline_behavior.go](pipeline_behavior.go) that does not nil-check its receiver, so chaining it onto a bare nil `PipelineBehavior` panics.
- **All database work goes through `builder.session()`.** Every builder carries the request's `data.Session`, and steps pass it to services (`modelService.ObjectSave(builder.session(), …)`) so the whole action shares one transaction. Never open a separate session inside a step.
- **`formdata.Parse` merges the URL query string into its result; `formdata.ParseBody` does not.** `Parse` returns `request.Form`, which is the query string plus the body, and a name present in both yields BOTH values — [step_EditRegistration.go](step_EditRegistration.go) depends on that merge to read its `registrationId` control parameter. For values supplied by an untrusted visitor, use `ParseBody`: a step that joins repeated values (as [step_ReadForm.go](step_ReadForm.go) does) would otherwise let a crafted link append its own text to a field the visitor believes is theirs, invisibly to them.
- **Request data reaches model objects only through the builder's schema.** `set-data` writes via `builder.schema().Set(object, path, value)` and the edit steps bind forms with `form.New(builder.schema(), …)`, so every write is validated, clamped, or rejected. Never copy request values onto a model object directly — that bypasses the only validation gate in the pipeline.
- **Step-argument templates are `text/template` — nothing they emit is HTML-escaped, and that is the point.** Step arguments (`values:`, `url:`, `message:`, …) are authored by template designers, who are trusted; the untrusted side is the data those templates pull from the builder. Safety comes from validating the *result*, not from escaping it — which is why `navigationURL` in [navigation.go](navigation.go) rejects targets that fail `uri.IsSafeRedirectURL`, since remote-influenced values (profile URLs, icon URLs) flow into `url:` templates and a `javascript:` scheme would otherwise become the redirect. Keep that check. Do NOT "harden" an argument by switching it to `html/template`: `redirect-to` parsed its `url` that way for years, and the contextual escaper silently turned every `&` into `&amp;` on its way into the `Location` header. Page views escape normally because `builder.execute()` renders through the Template's own `html/template`.
- **Navigation has two mechanisms, and choosing wrong fails silently.** An HTTP redirect is followed by whatever transport made the request — a browser navigates the document, but htmx's XHR follows it invisibly and swaps the response in as a *fragment*, which CORS makes impossible across origins. The `Hx-Redirect` header is executed by htmx itself and always navigates the document, but is inert for a plain `<a href>`. Neither failure produces an error: the first is a click that does nothing, the second is a blank 200. [navigation.go](navigation.go) owns the decision — `navigateContent` for `redirect-to` ("the content is elsewhere"), `navigateDocument` for `forward-to` ("the visitor goes elsewhere") — and each falls back to the other's mechanism where its own cannot work. Templates must not branch on `.IsPartialRequest` to work around this; if a case is not handled, fix the helper. See [README.md](README.md#navigation-redirect-to-vs-forward-to).
- **A step must never write to `builder.response()` for something the `PipelineResult` can carry.** `AsHTML` applies the result's headers and status *after* the pipeline finishes, so a step that calls `WriteHeader` itself commits the response early and silently discards the Content-Type and every `HX-Trigger` event earlier steps accumulated — plus echo logs `response already committed` when `ctx.HTML` runs. Return `Halt().AsFullPage().WithStatusCode(…).WithHeader(…)` instead. The steps that still write directly ([step_EditContent.go](step_EditContent.go), [step_Delete.go](step_Delete.go), [step_RequirePassword.go](step_RequirePassword.go)) are writing a response *body* — a separate, pre-existing pattern, not the headers-only case this rule is about.
- **A step's `method` does not stop the pipeline, and the defaults are not interchangeable.** [StepAsModal](step_AsModal.go) returns `AsFullPage()` *without* `Halt` on a partial GET, and `StepEditModelObject.Get` returns `nil`, so a `GET` that renders a modal form runs on through every step after it. Those steps skip themselves on their own `method`, which is why `forward-to` defaults to `post`: widening it to `both` would make the `circle-add` pipeline emit `Hx-Redirect` and navigate away before the modal ever rendered. All eight `method`-bearing steps parse through `parseMethod` in [../model/step/utils.go](../model/step/utils.go), which rejects anything but `get`/`post`/`both` at load time — the build-side guards are written in two different shapes (allow-list and deny-list) that read an unknown value in *opposite* directions, and that validation is what keeps them equivalent.
- **Per-widget behavior belongs in the widget's own `saveSteps` pipeline, never hardcoded into a Go step.** The stream template's `widget` action is shared by all widget types, so a widget-specific transform written into a step would run for every widget. The [Widget](builder_widget.go) sub-builder scopes the pipeline to one widget, and its steps address values as `data.{property}` because its `schema()` nests the widget definition's schema under `data`. These pipelines run from inside [StepSave](step_Save.go) via [executeWidgetSaveSteps](widget_save.go), before the Stream is written.
- **A page rendered by a handler instead of a Template action gets [Theme](builder_theme.go), or a builder that embeds it.** The Theme's shared partials — `includes-head` above all — call `.IsIndexable` and `.ThemeData` on their dot, and `html/template` resolves both at render time, so a dot missing either 500s the page in production rather than failing the build. The two shapes fail differently, which is what hides it: a no-argument lookup against a map yields nil silently, while `.ThemeData "token"` — the same lookup *with* an argument — is a hard error. `Theme` also owns the `IsIndexable() = FALSE` rule that keeps authentication and transaction pages out of the search index (`Common` defaults to TRUE), so [PasswordReset](builder_passwordReset.go) and [OAuthAuthorization](builder_oAuthAuthorization.go) inherit it by embedding `Theme` rather than restating it. Nothing types this boundary — `executeThemeTemplate` takes `any`, because an interface could only prove two methods exist, not that the dot is the right one. The parse-tree walk in [../handler/themeTemplate_test.go](../handler/themeTemplate_test.go) is the enforcement: it checks every accessor a template actually calls, and fails if a template rendering `includes-head` has no dot mapped to it.
- **The six `reset-*` templates deliberately split across two builders.** `reset-code*` uses `PasswordReset`, which carries the loaded User; `reset-password`/`reset-error`/`reset-confirm` use a plain `Theme`, which has no `Username()`. That is not an oversight — `PostResetPassword` renders `reset-confirm` on BOTH the found and not-found paths, so putting the User within reach of that template would make an account-existence oracle one edit away. Do not "tidy" the three onto `PasswordReset`.
- **Builders are value types — cross-call state lives only in the shared `arguments` map.** `setString`/`SetContent` work because `mapof.String` is a reference type; assigning to pointer fields on a value receiver (the `_user`/`_identity` caches in `getUser`/`getIdentity`) does not persist across calls, so never rely on those as caches or add new state that way.
- **`RelativeURL()` for form actions and htmx targets; `URL()`/`Host()` only for canonical links, og tags, and email.** `Host()` derives its port from the browser's request so absolute URLs survive proxies and port-maps, but the browser supplying its own origin is still the only always-correct source — hardcoding `Host()` into a form action breaks on non-standard ports.
- **Validation errors on htmx POSTs return HTTP 200 through `WrapInlineError` — that is not a bug.** The forms built by `WrapForm` use `hx-swap="none"`, so a bare 422 is silently discarded and the Save button looks dead. `AsHTML` in [utilities.go](utilities.go) retargets the message into `#htmx-response-message` instead; `inlineErrorMessage` hoists the root message of a validation chain because that is the half written for humans. The explicit `text/html` Content-Type must stay — Go's sniffer does not recognize a leading `<span` as HTML.
- **[StepViewHTML](step_ViewHTML.go) publishes ETag/Last-Modified but deliberately never answers 304.** An index page goes stale when a child changes and nothing invalidates the parent, so a conditional-request "optimization" would serve listings missing their newest entries. The default Cache-Control that denies caching is equally load-bearing.
- **Builders expose only the methods their templates actually call.** [builder_user_notifications.go](builder_user_notifications.go) is intentionally minimal — do not "complete" it by copying methods from the Inbox builder (or vice versa); a full copy rots. Its `notificationTabTypes`/`notificationTypeFilter` helpers are package-level because [step_MarkNotificationsRead.go](step_MarkNotificationsRead.go) shares them — keep exactly one definition, in that file.
- **`NewStream` enforces `UserCan(actionID)` at construction, and `View()`/`clone()` re-run it.** Permission checking happens when a builder is created, not when it renders — any new path that constructs a Stream builder for a different action must go through `NewStream` (or an equivalent gate), never by copying fields into a fresh struct.
