# Follow Button

This widget (widgetId `follow`) places a button on a Stream that opens the "Follow" window for a person on this server, giving visitors the same ActivityPub-or-email choice they would get from that person's profile page. Use it to invite readers of a page to subscribe to its author, or to any other local account.

[widget.hjson](widget.hjson) defines a three-field schema — `username` (the local account to follow), `label` (the text on the button), and `class` (an optional CSS class) — edited through a vertical form of text inputs. None is `required`, because a widget dragged onto the page and saved before it is filled in must still save; the empty cases are handled at render time instead. `username` uses rosetta's `username` format, which admits only letters, numbers, and underscores, and that restriction is what makes the value safe to interpolate directly into a URL in the markup.

[widget.html](widget.html) reads the settings with `.Widget.Data.GetString` and renders `<button hx-get="/@{username}/follow" class="primary">`. That route is `/@:userId/:action`, which resolves its token through `User.LoadByToken` — an ObjectID first, then a username — so a plain username is a valid address for it. The `follow` action on [user-outbox](../user-outbox/template.hjson) is wrapped in `as-modal`, and [StepAsModal](../../../build/step_AsModal.go) answers with its own `HX-Retarget: aside` and `HX-Reswap: innerHTML` headers; the button therefore must **not** declare an `hx-target` of its own, and does not. It does declare `hx-push-url="false"`, because that is the one header `as-modal` withholds when an action has a `background` view — and `follow` has one. This widget is the only caller of that action from a page that is not the profile, so without the attribute, opening the modal would move the address bar to the profile while the visitor is still reading the article underneath.

`class` goes on an unconditional wrapper `<div>` outside the widget's own `.widget-follow` element, rather than being merged onto it. Keeping them apart means a page stylesheet and the widget's own hooks are never selecting the same element, and the wrapper stays in the DOM when the class is cleared so a rule written against the structure keeps matching. Its schema format is `regex=^[\s\p{L}\p{N}_-]*$` — letters in any script, digits, `_`, `-`, and the whitespace that separates several classes. That is not what prevents an attribute breakout (html/template escapes the value in attribute context regardless); it is what keeps a styling hook from becoming a place to park arbitrary text. Note the doubled backslashes in the hjson source: hjson unescapes them, so the pattern the schema compiles is the single-backslash form. There is no named format for this in rosetta, so the regex is written out in full; a `css-class` format there would be the natural place for it once a second widget wants the same field.

An empty `label` falls back to the word "Follow". An empty `username` has no such fallback — there is nobody to follow — so the widget renders a short explanation in place of the button, and only for a visitor who `UserCan "edit"` the Stream. Everyone else sees nothing at all, on the principle that a configuration mistake is for the author to see and not the public. That note is deliberately left outside the `class` wrapper — it is a diagnostic rather than the widget, and a class that positions or hides the button must not be able to hide it.

The username field carries `validator:"/.validate/user/exists"`, so the editor checks the name against the server as it is typed and marks the field with a green check or a red X — the same mechanism the signup form and the Token/Slug fields use, driven by the `validator` hyperscript behavior in [theme-global](../theme-global/hyperscript/validator._hs). [GetValidateUserExists](../../../handler/validate.go) resolves the value through `User.LoadByToken`, exactly as the `/@:userId` route will, so the validator and the URL it is vetting cannot disagree about who exists. Unlike a Template's form, a widget's form is **not** rendered as a template — [StepEditWidget](../../../build/step_EditWidget.go) hands `widget.Form` straight to `form.Editor`, with no equivalent of `StepEditModelObject.executeOptionTemplates` — so a `{{...}}` written into an option here would reach the browser verbatim. This validator's URL takes no parameters, which is why it does not need one.

The behavior calls `setCustomValidity` with the failure message, so a red X does not merely warn — htmx runs HTML5 validation before it posts a form, and an unrecognized username therefore blocks the save. A blank username is still saveable, because the behavior exits before it fetches when the field is empty; that is the case widget.html handles.

What remains unguarded is the server side and the passage of time. Nothing re-checks a widget whose user was renamed or deleted after it was saved, and nothing rejects a POST that skips the browser; the button then opens a modal that 404s. Closing that would need a save-time check in the widget's `saveSteps`, or a `users` entry in [service/lookupProvider.go](../../../service/lookupProvider.go) so the form could offer a picker instead of free text.
