# Follow Button

This widget (widgetId `follow`) places a button on a Stream that opens the "Follow" window for a person on this server, giving visitors the same ActivityPub-or-email choice they would get from that person's profile page. Use it to invite readers of a page to subscribe to its author, or to any other local account.

[widget.hjson](widget.hjson) defines a four-field schema — `username` (the local account to follow), `label` (the text on the button), and `class` / `style` (optional styling hooks) — edited through a `layout-tabs` form with a **Button** tab and a **Stylesheet** tab. `LayoutTabs` takes each tab's name from its child element's `Label`, so a `layout-vertical` with no label silently renders as "Tab 0". No field is `required`, because a widget dragged onto the page and saved before it is filled in must still save; the empty cases are handled at render time instead. `username` uses rosetta's `username` format, which admits only letters, numbers, and underscores, and that restriction is what makes the value safe to interpolate directly into a URL in the markup.

[widget.html](widget.html) reads the settings with `.Widget.Data.GetString` and renders `<button hx-get="/@{username}/follow" class="primary">`. That route is `/@:userId/:action`, which resolves its token through `User.LoadByToken` — an ObjectID first, then a username — so a plain username is a valid address for it. The `follow` action on [user-outbox](../user-outbox/template.hjson) is wrapped in `as-modal`, and [StepAsModal](../../../build/step_AsModal.go) answers with its own `HX-Retarget: aside` and `HX-Reswap: innerHTML` headers; the button therefore must **not** declare an `hx-target` of its own, and does not. It does declare `hx-push-url="false"`, because that is the one header `as-modal` withholds when an action has a `background` view — and `follow` has one. This widget is the only caller of that action from a page that is not the profile, so without the attribute, opening the modal would move the address bar to the profile while the visitor is still reading the article underneath.

Both styling hooks land on the widget's own `.widget-follow` element, appended to its built-in classes rather than replacing them.

`class` uses the schema format `regex=^[\s\p{L}\p{N}_-]*$` — letters in any script, digits, `_`, `-`, and the whitespace that separates several classes. That is not what prevents an attribute breakout (html/template escapes the value in attribute context regardless); it is what keeps a styling hook from becoming a place to park arbitrary text. Note the doubled backslashes in the hjson source: hjson unescapes them, so the pattern the schema compiles is the single-backslash form. There is no named format for this in rosetta, so the regex is written out in full; a `css-class` format there would be the natural home once a second widget wants the same field.

`style` uses `css-declarations`, a rosetta format added for this field. Two things about it are worth knowing before touching either end:

- **It is not interchangeable with `css`.** `css` parses rule structure, so a bare declaration list has no selector or block in it and sanitizes to `""`; `css-declarations` filters declarations, so a stylesheet's braces and selector are not properties and it empties too. Both return a nil error either way, so pointing the schema at the wrong one does not fail — it silently stores an empty string. The two share the same property and value allowlists, so they agree about what is *safe*; they disagree only about what *shape* the input is.
- **The value must be piped through `css` in the markup.** `html/template` reads a `style` attribute as CSS context and runs its own value filter there, which replaces a plain declaration list with the literal text `ZgotmplZ` — the attribute never works at all, and nothing errors. The trust cast is safe for two independent reasons: the schema has already sanitized the value, and `html/template` still HTML-escapes a `template.CSS` value in attribute context, so a quote cannot break out regardless.

Because it shares the stylesheet allowlists, this field carries exactly the authority an author already has over a page stylesheet, and no more: `position:fixed` is dropped (it would let a widget lift itself out of the flow and cover unrelated page chrome), and any declaration naming a `url()` is dropped (it would make every page view fetch a third-party resource). Both are stripped in place, leaving the rest of the declarations intact.

An empty `label` falls back to the word "Follow". An empty `username` has no such fallback — there is nobody to follow — so the widget renders a short explanation in place of the button, and only for a visitor who `UserCan "edit"` the Stream. Everyone else sees nothing at all, on the principle that a configuration mistake is for the author to see and not the public. That note carries neither `class` nor `style` — it is a diagnostic rather than the widget, and styling that positions or hides the button must not be able to hide it.

The username field carries `validator:"/.validate/user/exists"`, so the editor checks the name against the server as it is typed and marks the field with a green check or a red X — the same mechanism the signup form and the Token/Slug fields use, driven by the `validator` hyperscript behavior in [theme-global](../theme-global/hyperscript/validator._hs). [GetValidateUserExists](../../../handler/validate.go) resolves the value through `User.LoadByToken`, exactly as the `/@:userId` route will, so the validator and the URL it is vetting cannot disagree about who exists. Unlike a Template's form, a widget's form is **not** rendered as a template — [StepEditWidget](../../../build/step_EditWidget.go) hands `widget.Form` straight to `form.Editor`, with no equivalent of `StepEditModelObject.executeOptionTemplates` — so a `{{...}}` written into an option here would reach the browser verbatim. This validator's URL takes no parameters, which is why it does not need one.

The behavior calls `setCustomValidity` with the failure message, so a red X does not merely warn — htmx runs HTML5 validation before it posts a form, and an unrecognized username therefore blocks the save. A blank username is still saveable, because the behavior exits before it fetches when the field is empty; that is the case widget.html handles.

One trap sits in the tests rather than the code: `schema.Validate` answers "does this value already conform", so it reports an **error** for anything a sanitizing format had to rewrite — `style` fails it even when sanitizing worked perfectly. `Set` is the call that rewrites in place, and the one [StepEditWidget](../../../build/step_EditWidget.go) actually makes, so the save path is unaffected and assertions belong against `form.SetURLValues`, not `Validate`. Note also that `SetURLValues` resolves each element's `Type` through the form registry, which is populated by `widget.UseAll()` rather than an `init()`; a test that forgets it fails on *every* element with "Unable to locate widget for element".

What remains unguarded is the server side and the passage of time. Nothing re-checks a widget whose user was renamed or deleted after it was saved, and nothing rejects a POST that skips the browser; the button then opens a modal that 404s. Closing that would need a save-time check in the widget's `saveSteps`, or a `users` entry in [service/lookupProvider.go](../../../service/lookupProvider.go) so the form could offer a picker instead of free text.
