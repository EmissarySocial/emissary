# Widget Editor (Base Template)

Shared base template (category: Base, model: Stream) that provides the drag-and-drop widget-placement editor used by any Stream template that supports widgets. Templates absorb it by listing `base-widget-editor` in their `extends` array; the embedded consumers are `stream-article-base` (and through it the article variants), `stream-folder`, and `stream-contact-form`.

[template.hjson](template.hjson) declares the default `widget-locations` (LEFT, TOP, RIGHT, BOTTOM) and two asset bundles — [stylesheet/editor.css](stylesheet/editor.css) and [hyperscript/widgetEditor._hs](hyperscript/widgetEditor._hs) — which are served at `/.templates/base-widget-editor/stylesheet` and `/.templates/base-widget-editor/hyperscript`. It defines no actions of its own: it only contributes the HTML definitions [widgets-list.html](widgets-list.html) (the full editor, which loads Sortable.js plus the bundles and posts widget placements to `/{streamId}/widgets`) and [widget.html](widget.html) (a single draggable widget chip with an optional Edit button). Extending templates wire these up by defining their own `widgets` action (using the `sort-widgets` step) and `widget` action (using the `edit-widget` step), and may override the `widget-locations` list to restrict where widgets can be placed.

A template may also ship a `layout-controls.html` into the slot the canvas reserves for controls that change the *shape* of the page. [layout-controls.html](layout-controls.html) is the empty default; [layout-controls-width.html](layout-controls-width.html) is a reusable page-width control that a template opts into by defining its own slot containing nothing but a call to it.

## What the canvas asserts, and what it does not

The canvas is a diagram of the page, not a preview of one viewport — so a few things are stated rather than drawn, and the stylesheet carries the reasoning for each:

- **A save is acknowledged in a fixed slot at the top.** `StepSortWidgets` answers a reorder, a move, or a layout change with `HX-Reswap: none`, deliberately, so that a redraw cannot destroy a drag still in flight. That leaves those saves invisible, so the behavior writes "Saved" (or "Save failed") into `.widget-editor-status` off htmx's own request events. The slot keeps its height whether or not it holds text, because it sits above every drop zone. It does not cover *creating* a widget: that is the one path still redrawn, and the swap destroys the marker — but creation shows itself, since the canvas visibly changes and the new chip arrives with an Edit button.
- **An empty sidebar collapses to a 16px rail.** An empty region renders nothing at all on the page, so a full-width empty column would be a lie about the result. 16px is a trial value.
- **Both sidebars carry a note about narrow screens.** Below 768px the page stops being three columns and the regions stack in DOM order — LEFT above the content, RIGHT below it — which nothing in a desktop editing session would otherwise show.
- **Nothing changes size while a drag is in flight.** The rail, the note, and the tray are all frozen for the duration of a gesture: a box that grew or shrank mid-drag would move every drop zone out from under the cursor.
