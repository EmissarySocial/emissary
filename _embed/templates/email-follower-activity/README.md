# Follower Activity Email

Notifies an email-method Follower that the account or stream they subscribe to has published a post. Outbox2's `Outbox2-Email` task (`Outbox2.SendEmail` in service/outbox2_delivery.go) and the legacy follower loop (service/outbox_delivery.go) both call `DomainEmail.SendFollowerActivity` (service/domainEmail.go), which sends one message per email Follower with the subject "New Activity From {{.Actor.Name}}" and a `List-Unsubscribe` header populated from the Follower's unsubscribe link. An activity that brings no post, such as a Delete, an Undo, or a post with neither a name nor content, sends nothing; `followerPost` decides.

This is the only shipped email that declares a `headers:` block, and until `applyHeaders` was added to `ServerEmail.Send` those templates were parsed and then discarded, so the header had never actually been sent.

The unsubscribe URL reaches the template in two forms, because its two consumers need different ones: the body renders `{{.Unsubscribe}}` bare inside an `href`, while the `List-Unsubscribe` header needs it inside the angle brackets RFC 2369 requires. `Follower.UnsubscribeLinkWithBrackets` (model/follower.go) supplies the second, derived from `UnsubscribeLink` so the two can never disagree about the URL itself.

Both forms are always populated. `UnsubscribeLink` builds a URL for every Follower rather than returning `""` for non-email methods, because the URL is public and can be typed by hand — withholding the string would have looked like an authorization check without being one. The real gate is `Follower.LoadBySecret` (service/follower_.go), which queries `method == EMAIL` alongside the ID and then compares the secret, so a non-email record cannot be reached through `follower-unsubscribe` or `follower-confirm` at all. That is what lets `List-Unsubscribe-Post` be an unconditional literal here: `List-Unsubscribe` is never absent from this message, so one-click never announces an address that was not sent. `TestFollowerActivity_ListUnsubscribe` and `TestFollowerActivity_OneClickRequiresLink` (service/serverEmail_test.go) pin the pairing; `TestFollowerLoadBySecret_RejectsOtherMethods` (service/follower_test.go) pins the gate.

[email.hjson](email.hjson) declares the `follower-activity` emailId, the `Follower` model guard, and the to/subject/header templates; [body.html](body.html) is a Go html/template rendered by `ServerEmail.Send` (service/serverEmail.go) with the shared funcMap (it uses `htmlMinimal` to sanitize the post's content). `followerActivityValues` in service/domainEmail.go builds the data map, and every key in it is always present: `Title`, `ContentHTML`, and `URL` (the post's `name`, `content`, and `id`, never its `url`, which for an Audio Stream is the media file), `Actor` (the `model.PersonLink` of the User or Stream the Follower follows, so the body reads `.Actor.Name` and `.Actor.IconURL`), `Name`, `Email`, `FollowerID`, `Secret`, `ParentLink`, `Unsubscribe`, and `UnsubscribeWithBrackets`, plus `Domain_Owner`, `Domain_URL`, `Domain_Name`, and `Domain_Icon` from `DomainEmail.Send`. The body never receives the activity itself. It wraps each optional part in `{{with}}`, because `html/template` prints a missing or empty value as `""` but `htmlMinimal` refuses a missing one, which is how a post with no body failed for every subscriber until BUG-372. `TestFollowerActivity_RendersEveryShape` (service/domainEmail_test.go) renders this body for every kind of post.
