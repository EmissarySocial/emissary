# theme-global — Agent Notes

See [README.md](README.md) for what the theme is and what each numbered stylesheet covers. These are the rules behind it that look removable and are not.

## Every dark-mode gray is hue 0, and a one-digit slip is invisible until it is ugly

The gray ramp in [stylesheet/01-colors.css](stylesheet/01-colors.css) is IBM's **warm gray**, not IBM's neutral gray, and the dark block inverts it. Warm gray is defined by red sitting above green and blue while **green and blue stay equal** — hue 0 in HSL. That equality is the whole rule: it is the only way a 17-step ramp reads as one family, and at these saturations (2% to 7%) it is also the only property a reader can perceive. Brightness differences look intentional; hue differences look like dirt.

A wrong digit in the green channel does not break the ramp visibly on its own step. It breaks the *transition* to the steps beside it, and only where two of them meet on screen. `#171714` instead of `#171414` moves gray00 from hue 0 to hue 60, which is olive, and at 8% lightness nothing about it reads as "green" in isolation; it reads as a smudge next to gray05. Six steps drifted this way before anyone could name what was wrong with the backgrounds, and gray60 had separately been filled from the neutral ramp (`#a8a8a8`, the light-mode gray40) instead of warm-gray-40, putting a colorless hole in the middle of a warm scale.

So: when you add or edit a dark gray, check `G == B` before checking anything else, and take new values from IBM warm gray rather than IBM gray. Eight of the steps are IBM warm gray exactly (`#ada8a8`, `#8f8b8b`, `#726e6e`, `#565151`, `#3c3838`, `#272525`, `#171414` and the three light steps rounded to hue 0), and the in-between steps (gray01 through gray05, gray15) are interpolations along the same line. Light mode is the opposite convention and is correct as it stands: it is IBM's **neutral** gray, every step fully desaturated, and warming it would be a separate design decision rather than a fix.

Nothing catches a violation. CSS has no notion of a palette, the ramp is not covered by a test, and the defect only shows up as an unpleasant page that no one can quite diagnose.

## `--white` and `--black` are pure white and pure black in both schemes

`--white` is always `#ffffff` and `--black` always `#000000`; the dark block does not redefine either. Use them only for color on something that keeps its color in both schemes: a photo, a map, or an accent that stays saturated in dark mode. The page's own surfaces and the text on them use `--gray00` and `--gray100`, which flip.

- **The color ramps flip unevenly.** In dark mode the -70 steps turn light, `--blue50` and `--red50` turn darker, and `--blue60` stays the same, so check a background's dark value before choosing `--white` or `--gray00` for the text on it.
- **The dark ramp's top is `#fffafa`, not pure white.** Pure white is the only color at L\* 100, so carrying the ramp's warmth all the way up costs a little brightness. `#fffafa` spends 1.4 L\* to land at chroma 1.76, matching `--gray90`'s 1.77 exactly, and the contrast against the page only moves from 18.3:1 to 17.7:1.
- **`--button-primary-color` stays a literal `#ffffff`.** Some themes outside Emissary still redefine `--white` per scheme, and `var(--white)` there would turn the label dark on a saturated button.

## The extended palette is a second, unrelated ramp

[stylesheet/01-more-colors.css](stylesheet/01-more-colors.css) defines `--color-gray-50`…`--color-gray-900` in a Spectrum-style scale, and those grays are **neutral in both schemes**. They are not the same family as `--gray00`…`--gray100` and do not follow the warm-gray rule above. Mixing the two ramps in one component is what makes a panel look subtly cold against its own page; pick one ramp per surface.

## Every file in `javascript/` ends with a semicolon

The `javascript` bundle joins its files with nothing between them, and the minifier then reads the result as one program. A file ending in `})()` followed by one starting with `(function` becomes `…})()(function…`, a call on the first file's return value: it throws, and every script after it in the bundle (turboclick, for one) silently never runs. `prism.js` was first written this way during EMISSARY-DEV-WEBSITE §1.7, and only running the minified bundle caught it. [service/theme_javascript_bundle_test.go](../../../service/theme_javascript_bundle_test.go) checks every bundled javascript file under `_embed/templates`.

## A `js` block in a `._hs` file ends at the first bare `end`, and only `//` comments are safe inside it

Hyperscript 0.9.93 does not parse the JavaScript in a `js` block. It runs its own tokenizer over it and stops at the first identifier token `end`, then hands everything before it to `new Function`. Its tokenizer knows `--` and `//` comments, and reads `/* */` as code, so an apostrophe inside a slash-star comment opens a string that swallows the rest of the block, and the word `end` inside one closes it early. Either way the whole hyperscript bundle fails, and every behavior on the page stops installing.

- **Use `//` comments only** inside a `js` block, and plain quoted strings. The tokenizer reads `'…'` and `"…"` as strings, as JavaScript does; template and regex literals have not been checked, and `list._hs` uses neither.
- **Never name anything `end`,** a variable or a property (`x.end`). `selectionEnd` is safe, because it is one identifier.
- **Every function declared in a top-level `js` block becomes global,** for every behavior in the bundle. `showIf._hs` declares `parse` and `split`, so a new block prefixes its functions with its behavior's name, as `list._hs` does with `listWidget`. A `const` in the block stays private to it.

## The `list` widget's rules are shared with the form library

[hyperscript/list._hs](hyperscript/list._hs) drives the `list` widget that `benpate/form` draws, with the styles in [stylesheet/03-widgets-list.css](stylesheet/03-widgets-list.css).

- **The repeat mark mirrors the server's cleanup.** The form library's `cleanList` trims each value, drops blanks, and drops a repeat by `strings.ToLower`, keeping the first, and the behavior marks a repeat by `toLowerCase()` and counts kept values the same way. Change both together (form's AGENTS.md has the same rule). The two folds differ for a few characters, such as the Turkish dotted İ, where the server decides.
- **The minimum is checked in the browser, because the server would drop the field.** rosetta refuses an Array short of its `minLength` or `required`, and `SetURLValues` logs that at debug level and saves nothing for the field. So the behavior sets a custom validity on the first row whenever the kept values fall short, and clears it on every change.
- **A list inside a hidden tab must not use `required`, `minLength`, or an item `pattern`.** The browser cannot focus an invalid control in a `hidden` tab panel, and `TabContainer` does not reveal one, so the Save does nothing and shows no message. Qwertylicious' featured hashtags sit in a tab and set none of the three.
- **Its rows are found from the widget, never by a document-wide query.** Each handler starts from `me`, and `listWidgetRowOf` refuses a row whose table is not the widget's own, so a list inside a table cell never reaches the table around it.
- **The focus ring is the row's, not the input's.** `tr.grid-row:has(input:focus)` draws `.input`'s ring around the whole row, grip and X included, and red while the row is invalid, and the grid's own ring on the focused cell is turned off. An outline on a `<tr>` draws in Chromium and WebKit; `.input` itself cannot go on the row, because a table row takes no padding or radius.
- **The X is a round button in the host theme's colors, named with `!important`.** `.grid button` strips the theme's look from every button in a grid, so the X sets its own from `--button-background`, `--button-background-hover`, and `--button-color`, which qwerty-theme defines, falling back to theme-global's grays. The `!important` is for the reason in "The `upload-multiple` X names its colors with `!important`" below.

## A chosen tab takes the focus into its panel, and the tab chosen on load never does

`TabContainer` ([hyperscript/tabs._hs](hyperscript/tabs._hs)) sends `selectTab(moveFocus:true)` for a click, or for Enter or Space on a focused tab, which the browser turns into a click, and `selectTab` then focuses the first control in the panel it shows: the first enabled input, select, textarea, button, link, or element with a `tabindex` that has a box (`tabContainerFocusFirst`). `init` sends `selectTab` with no `moveFocus`, so a page or a modal keeps its own focus when its tabs install; `Modal` focuses the modal's first input, and a tab that took the focus on load would fight it.

- **A tap never moves the focus** (`touchstart`), because a focused text field opens the on-screen keyboard over the panel the person just asked to see.
- **The flag is `moveFocus`, never `focus`,** which is a hyperscript command.

## A `def` that waits makes its caller wait, and an `on` handler queues behind it

Hyperscript's `call` awaits an async `def`, and a `def` becomes async as soon as it contains `wait`. An `on click` handler that calls one stays busy until the wait ends, and hyperscript queues every later click on that element behind it, so a second click looks ignored for seconds. 0.9.93 has no `async` command to detach the wait. [hyperscript/highlight._hs](hyperscript/highlight._hs) avoids waiting at all: its animation runs once and ends on the normal background, so `.flash-highlight` can stay on the element, and removing and re-adding it (with a layout read between) replays the flash.

Two more traps found on the way. `wait for animationend or 3s from node` parses without error but never times out; the timeout works only with an argument list, as in `wait for animationend(animationName) or 3s from node`. And `02-accessibility.css` shortens every animation to 0.01ms under `prefers-reduced-motion`, so an animation that carries meaning needs its own reduced-motion rule: `.flash-highlight` uses a class selector with `!important`, which outranks the universal one, and a `step-end` timing that holds the color without fading.

## The reduced-motion reset sets transitions to `0s`, never to a tiny duration

`transition-property` defaults to `all`, so a non-zero `transition-duration` on `*` gives every element a transition on every property, including the elements that never declared one. Most of them finish unseen. But Safari on iOS drew theme-minimal's mobile menu links in a stale, dark color on the dark background, until a scroll forced a repaint, while Web Inspector reported the correct white. It happened only in dark mode with Reduce Motion on, and removing the 0.01ms duration fixed it (*Ben, 2026-11-02*). Nothing in this repo listens for `transitionend`, and hyperscript's `transition` command stops waiting after 100ms when no transition starts, so no script waits on a transition that `0s` stops from running. Animations keep 0.01ms, because `animation-name` defaults to `none` and the same trap cannot occur.

## A request queued by `hx-sync` is dropped when its element leaves the document

htmx issues a queued request as a closure over the element that made it, and when its turn comes it first checks that the element is still in the document; one that is not is dropped, with no event and nothing in the console. The `upload-multiple` row and every X in it carry `hx-sync="closest .upload-multiple:queue all"`, and every response replaces the row, so an X clicked while a sort or an upload is in flight queues a delete that belongs to a button the response removes, and the delete never happens. The spec in qwertylicious found it by clicking an X right after a keyboard move (UPLOAD-MULTIPLE-WIDGET §1.10, 2026-11-04). [javascript/upload-multiple.js](javascript/upload-multiple.js) therefore holds every saved tile's X for the length of any request the zone makes, marks the zone `data-upload-multiple-busy`, and releases both when the zone is idle. Two rules keep the hold safe: a button is marked when the script disables it, so a release never enables one that is disabled for another reason, and `applyLimits`, which runs when a swapped-in row settles, leaves a held X alone and lets the minimum own a disabled X outright. Something that queues on a container the response replaces needs the same care, or its own queue, as the script's uploads have.

On a new object the row posts to the staging route instead and the response is one tile appended to the row (`beforeend`), so a queued delete there would survive; the hold is kept in both modes because one rule is easier to keep than two. The queue is the zone's, never the form's, and the form's Save is never held (Ben, 2026-11-04). The widget adds attachments to a saved object and touches no form data, so an upload must not depend on the form being saved, and the Save must not wait for an upload. The first build synced the row on `closest form` and held the Save with a "Wait for the files to finish" message, which made the two look coupled when they are not.

## The `upload-multiple` Save is stopped for the count, never for an upload

`guardSubmit` in [javascript/upload-multiple.js](javascript/upload-multiple.js) listens for `submit` on the document in the capture phase, so it runs before htmx's listener on the form, and stops a Save while a zone inside the form holds fewer files than its minimum or more than its maximum (Ben, 2026-11-04). This does not break the rule above that the Save is never held: that rule is about waiting for an upload, and this one is about the count. The guard counts the tiles with a `data-value`, the files the Save would leave in place, so a file still uploading is not counted and nothing waits for it.

- **It says why in two places.** The zone's status line shows the message, and so does `#htmx-response-message`, where `WrapInlineError` would put the server's refusal, because the zone may be on a tab that is hidden. The text is the step's own (`minimumMessage` and `maximumMessage`), so the browser and the server refuse in the same words.
- **The limits come from the row in both modes.** A saved object's row carries the step's limits, and a new object's row, which the same step draws when it is reached through the parent's add, carries them too; the zone carries nothing, since the widget became a loader on 2026-11-04.
- **A staged tile's X never locks at the minimum.** A create form's minimum is enforced at its Save, so removing the only staged file must still work. Only a saved object's Xs lock, because the step refuses a delete below the minimum there.
- **The widget's own requests ignore the count.** On a saved object an upload short of the minimum and a sort over the maximum both go through, because the step allows them, so a post outside its limits can be brought back within them.

## An `upload-multiple` zone takes no file while its form's Save is in flight

`onFormSending` in [javascript/upload-multiple.js](javascript/upload-multiple.js) marks every zone inside a form when that form's `htmx:beforeSend` fires, and `onFormSettled` clears the mark on its `htmx:afterRequest`. While a zone is marked, its plus is disabled, a drop is refused with a message, and a queued file waits. A file staged during a create form's Save is never adopted, because the Save has already posted its IDs. On a saved object, the widget's action can save the object while the form's Save writes it too: qwerty-photo's `photos` ends in `save`. The Save still never waits for an upload, as the rule above requires: an upload already in flight when the Save starts runs to the end.

- **Only the form's own request marks its zones.** The listeners sit on the document and check that `detail.elt` is a form, because every request made inside the form, the zone's own uploads included, names its own element (see the root AGENTS.md on a listener that hears every htmx request inside a form).
- **`htmx:beforeSend`, never `htmx:beforeRequest`.** A listener can cancel a request at `beforeRequest`, and a cancelled request never fires `afterRequest`, so a mark set there could refuse files until the page reloads. `beforeSend` fires only for a request that is sent, and `afterRequest` follows it on success, refusal, error, abort, and timeout.
- **A Save whose response removes the form clears nothing, and needs to clear nothing.** The `afterRequest` of a removed form never reaches the document, and its zones are gone with it.

## `htmx:abort` must reach the element that `hx-sync` keeps the request on

htmx keeps a request's `xhr` on the element named by `hx-sync`, not on the element that made the request, and its `htmx:abort` listener aborts only the `xhr` kept on the element the event reaches. The `upload-multiple` row syncs on `closest .upload-multiple`, so an abort triggered on the row aborted nothing: the upload finished, its tile arrived, and the "cancelled" file was there after all. The harness found it on 2026-11-04, as soon as a cancel on a new object left no row swap to hide it. `cancelUpload` in [javascript/upload-multiple.js](javascript/upload-multiple.js) triggers the abort on the zone, and anything else that cancels a synced request must trigger it on the sync element.

## The `upload-multiple` X is `.hover-show`, so nothing about it may depend on `display`

`.hover-show` in [stylesheet/03-widgets-hover.css](stylesheet/03-widgets-hover.css) hides an element with `display: none` on a device with a pointer, and shows it with `display: initial` while its `.hover-trigger` is hovered. `initial` is `inline`, which an absolutely positioned button blockifies to `block`, so a `display: inline-flex` on the X would lose to the utility's higher specificity on hover and its glyph would drop out of center. The X in [stylesheet/03-widgets-upload-multiple.css](stylesheet/03-widgets-upload-multiple.css) therefore sets no `display`, and the `<i>` inside it centers the glyph: an absolutely positioned flex box that fills the circle. The theme's buttons align their contents left and Bootstrap Icons nudge each glyph 0.125em below its line, which put the X near the circle's left edge until 2026-11-04. A hidden element cannot take focus either, so the tile shows its X on `:focus-within`, and [javascript/upload-multiple.js](javascript/upload-multiple.js) moves focus to a tile after a delete or a sort, never to an X; the tile is its own handle, with `tabindex="0"`, since Ben removed the handle buttons on 2026-11-04. A test that clicks an X in a browser with a pointer hovers its tile first.

The zone's status line is a `role="status"` live region, and an empty one used to hold a row of its own under the tiles, so the space below them was the padding plus the grid gap plus a line of text while the other three sides were the padding alone (Ben, 2026-11-04). `.upload-multiple-status:empty` is now `position: absolute`, which takes it out of the grid without taking it out of the page: an absolutely positioned child of a grid container makes no track and no gap, and the zone is `position: relative` to keep it inside. Do not hide it with `display: none` instead. A live region that is not rendered when its text arrives is not announced, so the sort and skip messages for keyboard users would go silent.

## The `upload-multiple` X names its colors with `!important`, because a theme's hover can outrank any class

The X is a black circle with a white glyph in every state (Ben, 2026-11-04), and no class selector can hold that on a qwertylicious page. qwerty-theme's `02-forms.css` styles buttons in one block whose selector list includes `#menu-bar button`, and nests `&:hover` inside it. A nested `&` resolves as `:is(...)`, which takes the specificity of its most specific argument, so that hover rule weighs one ID, one class, and one element for every button on the page, not only those in the menu bar. It turned the X light gray with a dark glyph under the mouse. [stylesheet/03-widgets-upload-multiple.css](stylesheet/03-widgets-upload-multiple.css) gives the X's `background-color` and `color` `!important`, the only weight a widget can count on against any theme. Its hover and focus ring is a `box-shadow`, which none of the global, default, or qwertylicious themes sets on a plain button (checked 2026-11-04).

## The `upload-multiple` zone is the grid, and its tile row has no box of its own

The zone is `display: grid`, and the row inside it, `.upload-multiple-tiles`, is `display: contents`, so the tiles are laid out as the zone's grid items and the plus tile, which the step draws right after the row, flows in after the last tile (Ben's sketch, 2026-11-04). The form library's `html-remote` draws only an empty shell that loads from the step, and the step draws the zone inside it (Ben, 2026-11-04). The zone keeps a tile's `min-height`, but the shell has no height of its own and no class to give it one, so the form grows when the zone arrives; the shell was the zone until 2026-11-04, when the `upload-multiple` widget that drew it left the form library. Because the zone now arrives in the same swap as its row, the script wires it only when htmx's `onLoad` runs after that swap settles, and marks it `data-upload-multiple-ready="true"`; a browser test that acts the instant the row is in the DOM lands on a zone with no listeners, so wait for the flag, as the qwertylicious spec does. The plus has to live outside the row because the step's response replaces the row with `outerHTML` on every change, and a row that was a grid of its own would push the plus onto a line of its own. Sortable still sorts the row's children with no box on the container, because it measures the tiles and not the row; verified in Chromium and WebKit in `pwtest2/probe` before the change. In a read-only view the row stands alone and is a grid itself, which is why the `display: contents` rule is scoped to `.upload-multiple > .upload-multiple-tiles`. The plus also needs its own `[hidden]` rule: its `display: flex` comes later in the cascade than normalize's `[hidden]`, so without it the script's `hidden` at the maximum would change nothing.

## Sortable loads once per page, through `sortContainer`

**A template installs `sortContainer` instead of loading Sortable with its own `<script src>`.** htmx runs every `<script src>` in swapped content again, so a list that carries one reloads Sortable.js whenever it is swapped back in: a tab opened a second time, or a form that answers each reorder with itself. Each run adds another copy of the library and another set of its page-wide listeners. `loadSortable()` in [hyperscript/sortcontainer._hs](hyperscript/sortcontainer._hs) adds the library to `<head>` once and fires `sortableReady` when it arrives. The `#sortable-library` id stops a second list from starting a second download while the first is still on its way.

**The `list` widget uses the same loader.** `ListWidget` calls `loadSortable()` when `window.Sortable` is missing, and attaches when `sortableReady` arrives.

**The loader lives in the hyperscript bundle, because both bundles load after `</body>`.** On a full page load, an inline `<script>` in the content runs before either bundle, so it cannot call a helper from them. Hyperscript initializes only once the page has parsed, so `sortContainer`'s `init` can always reach `loadSortable()`.

**`sortContainer` takes no arguments, and must keep taking none.** Hyperscript 0.9.93 throws when a behavior that declares parameters is installed without parentheses, so every bare `install sortContainer` would stop working, including any in a database-stored theme. Options travel as attributes instead: `data-sortable-handle` and `data-sortable-draggable`. An attribute left out keeps Sortable's own default, which matters for `draggable`: an undefined value would replace the default, and nothing would drag.

**Ten templates still load Sortable themselves, and install it their own way.** They are `user-inbox/newsfeed-menu.html`, `admin-navigation/index.html`, `stream-article-base/children-sort.html`, `base-widget-editor/widgets-list.html`, and six admin `index.html` pages (groups, webhooks, syndication, users, domain, and connections), which load it for `multiselect`. A page that mixes the two still works, because `loadSortable()` finds `window.Sortable` once any copy has run.
