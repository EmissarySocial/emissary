# Domain

The "General" tab of the admin console and its default landing page: `handler/admin.go` falls back to templateId `domain` when `/admin` is requested with no path segment, so this template serves `/admin` and `/admin/domain`. It edits the Domain record itself (`model: Domain`, built with `build.NewDomain`, owner-only): site label, theme, signup form, and the domain icon/image attachments, with a schema in [template.hjson](template.hjson) covering `label`, `themeId`, and the `signupForm` object.

The `index` action is a full pipeline rather than a plain view: [index.html](index.html) is the page shell (the menubar, then a Theme card showing the current theme's name and description), then `edit` appends the generated settings form, two `upload-attachments` steps handle the icon and image (webp, max 1 each, deletable via the `delete-icon`/`delete-image` actions), and `save` plus `startup-save-task` persist the change and tick the "/admin/domain" item on the startup checklist — with an `if` step branching between an inline save button and a "return to startup" link depending on `.IsDomainStartup`. Clicking the Theme card opens the three theme actions described below. Two more actions open modals or forms reused from elsewhere in the console: `defaults` edits the three start pages introduced by [defaults.html](defaults.html), and `signup` runs the `edit-registration` step for the signup form that admin-users links to. Extends `admin-common` for the shared menubar partial.

## Additional Information

### The index pipeline, step by step

The `index` action in [template.hjson](template.hjson) is one pipeline that serves both the GET (render) and POST (save) halves of the page; each build step decides per HTTP verb whether it participates, which is what makes the mixed view/edit/upload sequence work.

On GET: `view-html` renders [index.html](index.html) — the shell: the shared menubar, then the Theme card. Then `edit` (`build/step_EditModelObject.go`) generates the settings form; because the hjson supplies no `form`, `getForm` falls back to the `PropertyFormGetter` interface, and `Domain.PropertyForm()` in `build/builder_admin_domain.go` returns the current Theme's `Form` element — so the fields shown on the General page are defined by the active theme, not by this template. The step's two options are themselves templates: `{{if .NotDomainStartup}}cancel-button:hide{{end}}` hides the cancel button once the domain is live, and `cancel-href:/startup` points it at the startup checklist while setup is still running. Every later step in the pipeline is a no-op on GET.

On POST: `view-html` is skipped (its `method` defaults to `get`) and `edit` switches roles — it parses the form body and applies the values to the Domain object through the schema. The two `upload-attachments` steps are POST-only: each stores at most one uploaded file (icon and image, `accept-type: image/*`, stored per the `rules` as webp) and writes the resulting attachment ID into the `iconId`/`imageId` fields — the same fields the standalone `delete-icon`/`delete-image` actions clear with `delete-attachments`. `save` persists the Domain (POST-only by default; `model/step/save.go` defaults `method` to `"post"`), and `startup-save-task` appends `"/admin/domain"` to the Domain's completed-task list — silently skipping when the domain has left startup state or when the current theme does not define that task (`build/step_StartupSaveTask.go`). The `if` step evaluates `{{.IsDomainStartup}}` (`build/builder_common.go`), but both branch steps only write on POST: `inline-success` emits the "Return to Startup Checklist" link during startup, `inline-save-button` emits a fresh `install SaveButton` button otherwise. Finally `reload-page` answers with an `HX-Refresh: true` header so htmx reloads the whole page after a successful save.

### Changing the theme

Changing the theme takes three actions, and only the last one saves. The rules behind this shape are in [AGENTS.md](AGENTS.md).

1. **`themes`** opens a large modal over [themes.html](themes.html): a column with each visible theme's icon ([theme-icon.html](theme-icon.html)) and name. The current theme is drawn selected and does not respond to clicks. Each other theme is a button that opens step 2.
2. **`theme-confirm`** replaces the modal with [theme-confirm.html](theme-confirm.html), for the theme named in `?themeId=`: a Choose Theme link back to step 1, the new theme's name as the modal title, its `resources/startup/splash.png` (hidden when the theme ships none), its description, and Change Theme and Cancel buttons. For a theme that is current or not installed, it says so and offers only Cancel.
3. **`theme-switch`** is what the Change Theme button posts to, with the same `?themeId=`. When the theme is installed and not current, it writes `themeId` (`set-data from-url`), saves, and reloads the page, which now shows the new theme and its settings form. Otherwise it redraws `theme-confirm` inside the modal, which then explains the refusal.

A switch keeps the old theme's `themeData`, so its settings come back if the owner switches back. It creates no starter pages, because those are made only during startup. New users take their default folders, and any inbox or outbox their signup form leaves unset, from whichever theme is current when they sign up.

### Cross-template use of defaults and signup

Admin routing is purely positional — `server.go` registers `/admin/:param1/:param2`, and `handler/admin.go` maps the first segment to a templateId and the second to an actionID — so any admin page can invoke another template's actions with a plain htmx request, and two of this template's actions are shared that way. `admin-navigation/index.html` renders its "Start Pages" card as `hx-get="/admin/domain/defaults"`. `admin-sso/themes.html` posts a theme choice to `hx-post="/admin/domain/themes"` plus an `hx-vals` themeId, which saves nothing, because `themes` only draws the picker; nothing links to admin-sso's picker. `admin-users/index.html` renders its "New User Signups" card as `hx-get="/admin/domain/signup?registrationId=..."`.

The shared actions themselves: `defaults` opens a modal whose heading is [defaults.html](defaults.html) followed by an inline hjson form for the three start pages (`defaultAnonymous`, `defaultAuthenticated`, `defaultOwner`). `signup` runs `edit-registration` (`build/step_EditRegistration.go`), a step hard-restricted to the Domain builder that hand-builds a form listing every registration template from the Registration service, then `save` + `startup-save-task "/admin/domain/signup"` + `refresh-page`.
