# Domain

The "General" tab of the admin console and its default landing page: `handler/admin.go` falls back to templateId `domain` when `/admin` is requested with no path segment, so this template serves `/admin` and `/admin/domain`. It edits the Domain record itself (`model: Domain`, built with `build.NewDomain`, owner-only): site label, theme, signup form, and the domain icon/image attachments, with a schema in [template.hjson](template.hjson) covering `label`, `themeId`, and the `signupForm` object.

The `index` action is a full pipeline rather than a plain view: [index.html](index.html) is only the page shell (menubar plus an open card div), then `edit` appends the generated settings form, two `upload-attachments` steps handle the icon and image (webp, max 1 each, deletable via the `delete-icon`/`delete-image` actions), and `save` plus `startup-save-task` persist the change and tick the "/admin/domain" item on the startup checklist — with an `if` step branching between an inline save button and a "return to startup" link depending on `.IsDomainStartup`. Three more actions open modals or forms reused from elsewhere in the console: `themes` renders the theme picker in [themes.html](themes.html) (also targeted by `hx-post` buttons in admin-navigation and admin-sso), `defaults` edits the three start pages introduced by [defaults.html](defaults.html), and `signup` runs the `edit-registration` step for the signup form that admin-users links to. Extends `admin-common` for the shared menubar partial.

## Additional Information

### The index pipeline, step by step

The `index` action in [template.hjson](template.hjson) is one pipeline that serves both the GET (render) and POST (save) halves of the page; each build step decides per HTTP verb whether it participates, which is what makes the mixed view/edit/upload sequence work.

On GET: `view-html` renders [index.html](index.html) — only the shell (shared menubar, a `refreshPage` listener div, and the opening of the settings card). Then `edit` (`build/step_EditModelObject.go`) generates the settings form; because the hjson supplies no `form`, `getForm` falls back to the `PropertyFormGetter` interface, and `Domain.PropertyForm()` in `build/builder_admin_domain.go` returns the current Theme's `Form` element — so the fields shown on the General page are defined by the active theme, not by this template. The step's two options are themselves templates: `{{if .NotDomainStartup}}cancel-button:hide{{end}}` hides the cancel button once the domain is live, and `cancel-href:/startup` points it at the startup checklist while setup is still running. Every later step in the pipeline is a no-op on GET.

On POST: `view-html` runs again (its `method` is unset, so `StepViewHTML` executes for both verbs) and `edit` switches roles — it parses the form body and applies the values to the Domain object through the schema. The two `upload-attachments` steps are POST-only: each stores at most one uploaded file (icon and image, `accept-type: image/*`, stored per the `rules` as webp) and writes the resulting attachment ID into the `iconId`/`imageId` fields — the same fields the standalone `delete-icon`/`delete-image` actions clear with `delete-attachments`. `save` persists the Domain (POST-only by default; `model/step/save.go` defaults `method` to `"post"`), and `startup-save-task` appends `"/admin/domain"` to the Domain's completed-task list — silently skipping when the domain has left startup state or when the current theme does not define that task (`build/step_StartupSaveTask.go`). The `if` step evaluates `{{.IsDomainStartup}}` (`build/builder_common.go`), but both branch steps only write on POST: `inline-success` emits the "Return to Startup Checklist" link during startup, `inline-save-button` emits a fresh `install SaveButton` button otherwise. Finally `reload-page` answers with an `HX-Refresh: true` header so htmx reloads the whole page after a successful save.

### Cross-template use of themes, defaults, and signup

Admin routing is purely positional — `server.go` registers `/admin/:param1/:param2`, and `handler/admin.go` maps the first segment to a templateId and the second to an actionID — so any admin page can invoke another template's actions with a plain htmx request, and three of this template's actions are shared that way. `admin-navigation/index.html` renders its "Website Theme" card as `hx-get="/admin/domain/themes"` and its "Start Pages" card as `hx-get="/admin/domain/defaults"`. `admin-sso/themes.html` posts its theme choice to this template with `hx-post="/admin/domain/themes"` plus an `hx-vals` themeId — even though admin-sso declares a `themes` action of its own, its HTML submits back here. `admin-users/index.html` renders its "New User Signups" card as `hx-get="/admin/domain/signup?registrationId=..."`.

The shared actions themselves: `themes` opens a large modal over [themes.html](themes.html) (a radio list of installed `.Themes`), then `set-data from-form:["themeId"]` + `save` + `reload-page` on POST. `defaults` opens a modal whose heading is [defaults.html](defaults.html) followed by an inline hjson form for the three start pages (`defaultAnonymous`, `defaultAuthenticated`, `defaultOwner`). `signup` runs `edit-registration` (`build/step_EditRegistration.go`), a step hard-restricted to the Domain builder that hand-builds a form listing every registration template from the Registration service, then `save` + `startup-save-task "/admin/domain/signup"` + `refresh-page`.
