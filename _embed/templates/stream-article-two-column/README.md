# Two Column

This is the Two Column article type (`templateId: article-two-column`), for a page whose text runs in two side-by-side blocks rather than one. It extends `article-base` ([stream-article-base](../stream-article-base)), inheriting the article schema, `default`/`published` states, draft workflow, widget layout, and all viewing/publishing actions, and can be created under streams whose templateRole is `top`, `home`, `folder`, or `article` (`containedBy`). Like its siblings it re-declares `tagPaths: ["data.tags"]`, because tagPaths is deliberately not inherited through `extends`.

A Stream has one content area, so the two blocks are custom fields instead: `data.left` and `data.right`, each holding Markdown source. [editor.html](editor.html) gives each one an [EasyMDE](https://github.com/Ionaru/easy-markdown-editor) editor — the same toolbar, image upload, and save-on-blur behavior as [stream-article-markdown](../stream-article-markdown) — laid out at whatever proportion the article is set to, so the writing surface previews the result. [view.html](view.html) renders both through the `markdown` helper, which is the application's single converter and sanitizer, inside one `.e-content` so the h-entry still describes the whole article. Saving is `set-data` plus `save`, the same pipeline any other custom field uses.

Nothing writes `content.*`, which makes a Two Column article a **website page**: `content.HTML` is the body that ActivityPub, the Mastodon API, oEmbed, and link previews all read, and it stays empty here. Fill in the Summary on the Info tab, which is what those previews fall back to. Hashtags typed into the body are not linkified the way they are in a single-content article either — `data.tags` on the Info tab is what categorizes the page.

The split is `data.columns` — 2/3, 1/2, or 1/3 to the left column — and it is set from two places, which are the same control rather than two. **The edit page** puts it above the editors as three icons, so the proportion is chosen where the writing happens and the writing surface re-proportions on the click. **The Layout tab** shows the same picker beside **Page Width**, the shared Full/Large/Medium/Small control from [base-widget-editor](../base-widget-editor). The two settings compose: width sets how much of the page the article fills, the split divides it.

The icons are radios rather than a dropdown because an `<option>` cannot hold markup, and they are the SVGs in [resources/](resources) drawn as a CSS mask — see that folder's README for why an `<img>` would paint them black. Only Page Width is mirrored on the widget editor's canvas; the split is not.

On SMALL and EXTRA-SMALL pages — everything the design system puts under 768px — the columns reflow into rows, left above right. That is the same breakpoint and the same mechanism as every responsive utility in theme-global (`.md\:flex-row`, `.cols-*`): an `@container` query resolved against `.page`, so the article tracks the page the theme actually draws rather than the raw viewport.

Both surfaces that draw the split — the page and the editor — use one layout engine, flexbox with `flex-basis: 0`, from one bundled stylesheet: [stylesheet/two-column.css](stylesheet/two-column.css), served at `/.templates/article-two-column/stylesheet`. Its header carries the reasoning for both of those choices, including why the ratio is worthless without the zero basis.
