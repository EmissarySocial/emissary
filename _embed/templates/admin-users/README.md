# User

Admin console page for managing every user account on the domain, served at `/admin/users` under the "People > Users" sub-menu. [template.hjson](template.hjson) declares `model: User`, so `handler/admin.go` loads the User named by the URL's objectID and builds the page with `build.NewUser`; every action is owner-only, and the template declares the `LIVE` state that marks an account as activated.

The `index` action renders [index.html](index.html): a signup-settings card that jumps to admin-domain's `signup` action, user-count stats, an "Invite a Person" button, and a group/name filter feeding the `list` view; [list.html](list.html) pages 12 users at a time (`Top12.ByDisplayName`) with infinite scroll, per-row masquerade sign-in forms posting to `/.masquerade`, and special rendering for accounts with a `MovedTo` address. The `add` and `edit` actions open modals sharing a tabbed hjson form (general info, inbox/outbox template selection, groups, visibility toggles, and an owner grant); `add` deliberately finishes with `set-state: LIVE` because admin-created accounts skip the self-service onboarding wizard that normally performs that transition (the hjson comment documents the profile-500 bug this fixes), while `edit` first renders the heading in [edit.html](edit.html) with profile, Stripe, reset-password (`send-welcome` action), and masquerade shortcuts. There is also a modal-free `edit-form` variant, `send-welcome` (sends the "welcome" email), `delete`, and an orphaned [view.html](view.html) that no action references. Extends `admin-common` for the shared menubar partial.

## Additional Information

### The invite and edit forms

The `add` and `edit` actions in [template.hjson](template.hjson) carry near-identical `layout-tabs` forms defined inline in the hjson, rendered by the `edit` step (`build/step_EditModelObject.go`) inside an `as-modal` wrapper. The five tabs are: General (displayName, username, emailAddress), Profile (inboxTemplate and outboxTemplate selects fed by the `inbox-templates` and `outbox-templates` lookup providers), Groups (a multiselect fed by the `groups` provider), Visibility (isPublic, isBridgeBluesky, and isIndexable toggles), and Owner (the isOwner toggle that grants full domain control). `edit` differs from `add` in three ways: it first renders the heading in [edit.html](edit.html), it passes the option `delete:/admin/users/{{.UserID}}/delete` so the generated form includes a delete button, and it does not change state. `edit-form` is a modal-free variant with a shorter `layout-vertical` form that pins its own submit target via an `endpoint:` option.

### The LIVE-state activation workaround

The template's `states` block declares a single `LIVE` state, and the `add` pipeline runs `{do: "set-state", state: "LIVE"}` between the form and `save`. The comment in the hjson (labeled "FIX #2") explains what this works around: the self-service onboarding wizard is the only flow that moves a User into the `LIVE` state, and admin-created accounts never pass through it — so without this step they would remain pre-LIVE forever, and their profile page would render the self-only wizard branch, producing an HTTP 500 for every other viewer. `StepSetState.Post` (`build/step_SetState.go`) performs the transition through the builder's `StateSetter` interface before the object is saved.

### Masquerade, reset password, and Stripe

Both [list.html](list.html) rows and the [edit.html](edit.html) heading contain plain HTML forms that POST to `/.masquerade?userId=...`, an owner-only route registered in `server.go` and handled by `handler/signin_masquerade.go`: it builds masquerade JWT claims via `MasqueradeAs` and calls steranko's `PushCookie`, which stacks the administrator's own session into a "-backup" cookie slot so that signing out of the masqueraded session pops back to the administrator. The "Reset Password" button in edit.html posts to the `send-welcome` action, whose `send-email` step (`build/step_SendEmail.go`) calls `User.SendPasswordResetEmail` with the welcome-duration reset window and deliberately reports-and-continues on failure so a bounced email never fails the surrounding action. Finally, when the user's `MapIDs` contains a `STRIPE` key, edit.html links straight to that customer record in the Stripe dashboard — note the URL is hardcoded to the `/test/` (test-mode) dashboard.

### The infinite-scroll user list

[index.html](index.html) seeds `<table id="users">` with `{{.View "list"}}` and pairs it with a filter form (groupId select, name search) that re-fetches `/admin/users/list` into `#users` via `innerHTML` on change or keyup (throttled 500ms). Each [list.html](list.html) response renders up to 12 users (`.Users.Top12.ByDisplayName`) inside a `<tbody>` that itself carries `hx-trigger="revealed"` and `hx-swap="beforeend"` pointing at the next batch URL — forwarding the current groupId and search filters plus a cursor of `displayName=gt:{last displayName}` — so scrolling to the end of one batch appends the next, and the chain stops when a batch comes back empty because the whole file is wrapped in `{{if not $users.IsEmpty}}`. Server-side, `Users()` in `build/builder_admin_users.go` translates the query string into criteria with benpate/exp-builder: `search` aliases `displayName` with a contains default, `displayName` accepts operator-prefixed values (the `gt:` prefix parses into a greater-than expression), and `groupId` filters by ObjectID, all ANDed with `deleteDate == 0`. Rows for accounts with a `MovedTo` address render struck-through with a "New Profile" link in place of the per-row masquerade form, and the `highlight` helper marks the search term inside display names.
