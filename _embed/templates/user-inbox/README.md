# Default Inbox

The signed-in user's newsfeed at `/@me/newsfeed`: messages from everyone the user follows, organized into folders with a sidebar, three switchable layouts (SOCIAL, NEWSPAPER, MAGAZINE), and per-source filtering. [template.hjson](template.hjson) declares `templateRole: user-inbox` on the `Inbox` model (which operates on the User record — see `model/template.go`), and users can swap in any template with this role via the profile's edit-template step (`build/step_EditTemplate.go`). Every action is restricted to `roles: ["self"]`, and the template extends `base-social` for shared social fragments.

The page flow: the `index` action redirects bare URLs to the `feed` (all folders, zero folderId) or `folder` views, both of which render [index.html](index.html); that page lazy-loads [list.html](list.html), which picks a layout partial ([list-social.html](list-social.html), [list-newspaper.html](list-newspaper.html), or [list-magazine.html](list-magazine.html)) per the folder's `layout` setting and infinite-scrolls via the `list`/`list-before` actions. Opening a message runs the `browse` action as a modal, and the `browse-*` actions render remote ActivityPub documents, actors, conversations, and reply trees fetched on demand. Folder CRUD happens in the `folder-add`/`folder-edit`/`folder-delete` actions (inline forms in the hjson), and `folder-read` marks a folder read Mastodon-style when opened, firing `refreshSidebar`.

`reply` uses `add-stream` to post an `outbox-reply` stream into the user's outbox. The `stylesheet` and `hyperscript` bundles serve the files in [stylesheet/](stylesheet/) and [hyperscript/](hyperscript/) (keyboard/selection behaviors for list items) at `/.templates/user-inbox/...`. Note that "Follow Someone", source editing, and the actor view's Follow and Rule tabs link into the user-settings template (`/@me/settings/following-*` and `actor-rule`) rather than handling followings and rules here.

## Additional Information

### Folders, layouts, and the sidebar

Routing first: `index` only redirects — a bare `/@me/newsfeed` goes to `feed`, and a legacy `?folderId=` URL goes to `folder`. `feed` forces `folderId=000000000000000000000000` (the synthetic "all folders" entry) with `set-query-param` and renders [index.html](index.html); `folder` renders the same file for a single folder. [index.html](index.html) draws the sticky button bar (Follow Someone always; Filter and Folder Settings only when a real folder is selected), the folder heading (or a source heading when `?origin.followingId=` filters to one source), then lazy-loads the `list` action into the page. [list.html](list.html) branches on the folder's `layout` field: SOCIAL delegates the whole list to [list-social.html](list-social.html), while NEWSPAPER and MAGAZINE loop `.Inbox.Top12.ByPublishDate` themselves — defaulting `readDate=MAX`, wrapping each row in the htmx attributes that open the `browse` modal and install the `listItem` behavior, choosing [list-newspaper.html](list-newspaper.html) or [list-magazine.html](list-magazine.html) per row, and ending with an `intersect once` sentinel that fetches the next page via `list?rank=GT:{lastRank}&read=false&remote=true`. The red "Older Posts / New Posts" divider is a one-shot click target that inserts [list-before.html](list-before.html) content (`readDate=LT:{now}`) above the fold.

Folder management: `folder-add` and `folder-edit` run `with-folder` (which loads or creates the user's Folder from `?folderId=`, where `folderId=new` means create), open an `as-modal` inline form — name with a server-side validator at `/.validate/folder/name`, icon from the `navigation-icons` provider, layout enum — then `save` and `refresh-page`. `folder-delete` confirms (warning that the folder's inbox items go with it) and forwards to `feed`. The sidebar ([newsfeed-sidebar.html](newsfeed-sidebar.html) wrapping [newsfeed-menu.html](newsfeed-menu.html)) re-fetches itself on every `refreshSidebar` event so unread dots stay current; the folder list is a SortableJS-driven form that posts its `keys` order to `folder-sort` (`with-folder` + `sort`) when a drag ends. `folder-read` (`mark-folder-read` + `refreshSidebar`) is posted by index.html one second after a single folder opens, clearing that folder's unread dot Mastodon-style while the rendered rows keep their unread styling; it is skipped on the all-folders view. On mobile the sidebar is a separate page, [mobile.html](mobile.html).

### Reading messages

Every way into a post opens the `browse` modal described below: a click on a row in any layout, the "N Replies" link that [message-responses.html](message-responses.html) draws under a Social row, and the placeholder of a post hidden by the reader's rules. Read tracking is client-driven: the `listItem` behavior POSTs `message-read` as a row scrolls past, and `message-read` runs `with-message` + `set-state` (state READ), then saves and fires `refreshSidebar`. `with-message` scopes it to a Message owned by the signed-in user, loaded from `?messageId=`. The web inbox has no control that mutes a thread; the Mastodon API sets the MUTED state, and each layout labels such a row Notifications Muted.

### Browsing remote documents (browse-*)

The `browse-*` family renders live ActivityPub documents fetched from the network, not stored inbox rows. Every template starts with `.ActivityStream (.QueryParam "url")` — `build/builder_common.go` loads the URL through the server's shared ActivityStream cache with the viewer's moderation rules stamped into the document metadata, returns an empty document on failure (templates then render a "Document Not Found" card), and honors `?reveal=true` as a click-to-reveal that lifts only the viewer's own rule-hides. [browse.html](browse.html) dispatches: actors go to [browse-actor.html](browse-actor.html), everything else to [browse-tree.html](browse-tree.html). The shared [browse-header.html](browse-header.html) switches a modal between three layouts of the same URL, plus the private **Notes** tab described under "Annotations" below: Nested ([browse-tree.html](browse-tree.html) — the document plus its ancestors via [browse-parent.html](browse-parent.html), with replies lazy-loaded through [browse-tree-replies.html](browse-tree-replies.html)/[browse-tree-reply.html](browse-tree-reply.html)), Index ([browse-index.html](browse-index.html) — a flat timeline of the document's conversation via `.QueryByContext`), and Code ([browse-code.html](browse-code.html) — the raw JSON-LD, pretty-printed). [browse-document.html](browse-document.html) is the card partial both layouts share. [browse-actor.html](browse-actor.html) renders a remote profile with tabs that cross into other templates — Notes opens the private `annotation` editor here (see "Annotations" below), while Rule, Follow/Following, and Follows You open user-settings actions — and lazy-loads the actor's featured collection via [browse-actor-featured.html](browse-actor-featured.html). Only `browse`, `browse-actor`, and `browse-reply` open as modals; the rest are fragments swapped inside an already-open modal.

### Annotations

An annotation is a `model.Annotation`: one User's private record of one URL, with an optional note. It never federates. [annotation-button.html](annotation-button.html) is lazy-loaded next to the like button on every object the inbox renders (`browse-document`, `browse-tree-reply`, `message-responses`), and `base-social`'s `share-button` follows it, last in the row. The actor tab strips, here and in user-settings, show the same state on their **Notes** tab through `.Annotation`. Either state of the button opens `browse-annotation`, the way Reply opens `browse-reply`: [browse-annotation.html](browse-annotation.html) shows the post and its thread on top, and renders the `annotation-editor` action below it with `.View`. That form posts to `annotation-editor` through its `endpoint` option, not to the modal, because an `as-modal` POST always closes the modal. After saving, it renders [browse-annotation-modal.html](browse-annotation-modal.html), which calls `.View "browse-annotation"`: on an htmx request that returns the whole modal with `HX-Retarget: aside`, so the thread stays open and the tab bar's Notes / Noted label is current. `annotation-delete` does the same for a document, removing the `closeModal` its delete step adds; for an actor it closes the modal. The **Notes** tab of the document browser ([browse-header.html](browse-header.html)) opens the same view. The actor view's own **Notes** tab runs the older `annotation` action instead: [annotation.html](annotation.html) dispatches to [browse-actor-annotation.html](browse-actor-annotation.html), or for a document to [browse-document-annotation.html](browse-document-annotation.html), a card above the note, which no icon or tab links to any more. Saving with an empty note keeps the annotation, and only `annotation-delete` (the editor's Delete link) removes it. Internally these are annotations; every visible label calls them **Notes**. Only the Bootstrap icon is named `bookmark`.

Every change fires `trigger-event annotationChanged` with the URL as its value. The `annotationPeer` behavior in theme-global's hyperscript compares that value with each button's `data-annotation-url` and sends `refresh` to the matching ones, which re-fetch themselves through `annotation-button`. It lives in theme-global because user-notifications also opens these modals. The URL is read from the attribute rather than written into the `script`, because a remote URL can carry a quote.

The `annotations` action is the sidebar's **Notes** page ([annotations.html](annotations.html)). It sets `?section=ANNOTATIONS`, which `.FoldersWithSelection` and [newsfeed-menu.html](newsfeed-menu.html) use to highlight Notes instead of All Folders, and [newsfeed-sidebar.html](newsfeed-sidebar.html) carries it through its `refreshSidebar` re-fetch. [annotations-list.html](annotations-list.html) pages through `.Annotations` 30 rows at a time on `createDate`, narrowed by `?type=actor|document`. A row opens its annotation: an actor's row runs `annotation`, the actor view's **Notes** tab, and a post's row runs `browse-annotation`, the post with its note editor below.

### Replying

The `reply` action posts a new stream into the user's own outbox: `set-args` sets the composer's `postTo` URL, then `add-stream` with `style:"inline"`, `roles:"outbox-reply"`, and `location:"outbox"` renders an inline composer on GET and creates the Stream on POST (`build/step_AddStream.go`), pre-setting `inReplyTo` to the browsed document's permalink and redirecting back into `browse-tree` so the new reply appears in the conversation.

### The hyperscript bundle

[hyperscript/listitem._hs](hyperscript/listitem._hs) defines `listItem(messageId)`, installed on every list row: when the row scrolls off the top of the viewport it POSTs `message-read` once (guarded by a `data-read` attribute) and triggers `refreshSidebar` — scroll-past-marks-read. The `hyperscript` bundle concatenates the folder's hyperscript files, and index.html loads it as `/.templates/user-inbox/hyperscript`.
