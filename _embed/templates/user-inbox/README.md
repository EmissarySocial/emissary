# Default Inbox

The signed-in user's newsfeed at `/@me/newsfeed`: messages from everyone the user follows, organized into folders with a sidebar, three switchable layouts (SOCIAL, NEWSPAPER, MAGAZINE), and per-source filtering. [template.hjson](template.hjson) declares `templateRole: user-inbox` on the `Inbox` model (which operates on the User record — see `model/template.go`), and users can swap in any template with this role via the profile's edit-template step (`build/step_EditTemplate.go`). Every action is restricted to `roles: ["self"]`, and the template extends `base-social` for shared social fragments.

The page flow: the `index` action redirects bare URLs to the `feed` (all folders, zero folderId) or `folder` views, both of which render [index.html](index.html); that page lazy-loads [list.html](list.html), which picks a layout partial ([list-social.html](list-social.html), [list-newspaper.html](list-newspaper.html), or [list-magazine.html](list-magazine.html)) per the folder's `layout` setting and infinite-scrolls via the `list`/`list-before` actions. Opening a message runs the `message` action as a modal, and the `browse-*` actions render remote ActivityPub documents, actors, timelines, and reply trees fetched on demand. Folder CRUD happens in the `folder-add`/`folder-edit`/`folder-delete` actions (inline forms in the hjson), and `folder-read` marks a folder read Mastodon-style when opened, firing `refreshSidebar`.

The `actor-button-*` action family follows/unfollows (via `with-following`) and mutes/blocks/unblocks (via `with-rule`, saving ACTOR-type Rules), swapping button fragments in place; `reply` uses `add-stream` to post an `outbox-reply` stream into the user's outbox. The `stylesheet` and `hyperscript` bundles serve the files in [stylesheet/](stylesheet/) and [hyperscript/](hyperscript/) (keyboard/selection behaviors for list items) at `/.templates/user-inbox/...`. Note that "Follow Someone" and source editing link into the user-settings template (`/@me/settings/following-*`) rather than handling followings here.

## Additional Information

### Folders, layouts, and the sidebar

Routing first: `index` only redirects — a bare `/@me/newsfeed` goes to `feed`, and a legacy `?folderId=` URL goes to `folder`. `feed` forces `folderId=000000000000000000000000` (the synthetic "all folders" entry) with `set-query-param` and renders [index.html](index.html); `folder` renders the same file for a single folder. [index.html](index.html) draws the sticky button bar (Follow Someone always; Filter and Folder Settings only when a real folder is selected), the folder heading (or a source heading when `?origin.followingId=` filters to one source), then lazy-loads the `list` action into the page. [list.html](list.html) branches on the folder's `layout` field: SOCIAL delegates the whole list to [list-social.html](list-social.html), while NEWSPAPER and MAGAZINE loop `.Inbox.Top12.ByPublishDate` themselves — defaulting `readDate=MAX`, wrapping each row in the htmx attributes that open the `message` modal and install the `listItem` behavior, choosing [list-newspaper.html](list-newspaper.html) or [list-magazine.html](list-magazine.html) per row, and ending with an `intersect once` sentinel that fetches the next page via `list?rank=GT:{lastRank}&read=false&remote=true`. The red "Older Posts / New Posts" divider is a one-shot click target that inserts [list-before.html](list-before.html) content (`readDate=LT:{now}`) above the fold.

Folder management: `folder-add` and `folder-edit` run `with-folder` (which loads or creates the user's Folder from `?folderId=`, where `folderId=new` means create), open an `as-modal` inline form — name with a server-side validator at `/.validate/folder/name`, icon from the `folder-icons` provider, layout enum — then `save` and `refresh-page`. `folder-delete` confirms (warning that the folder's inbox items go with it) and forwards to `feed`. The sidebar ([newsfeed-sidebar.html](newsfeed-sidebar.html) wrapping [newsfeed-menu.html](newsfeed-menu.html)) re-fetches itself on every `refreshSidebar` event so unread dots stay current; the folder list is a SortableJS-driven form that posts its `keys` order to `folder-sort` (`with-folder` + `sort`) when a drag ends. `folder-read` (`mark-folder-read` + `refreshSidebar`) is posted by index.html one second after a single folder opens, clearing that folder's unread dot Mastodon-style while the rendered rows keep their unread styling; it is skipped on the all-folders view. On mobile the sidebar is a separate page, [mobile.html](mobile.html).

### Reading messages

Opening a row runs the `message` action: an `as-modal` render of [message.html](message.html), which loads the underlying document with `.ActivityStream` and shows Prev/Next buttons (`?sibling=prev|next`), the mute toggle fragment, Website/Code links, and a lazy-loaded reply thread via `responses-replies`. Read tracking is client-driven: the `message` hyperscript behavior POSTs `message-read` when the modal opens, and `message-read` itself runs `with-message` + `set-state` (state READ), then saves and fires `refreshSidebar`. `message-mute`/`message-unmute` flip the Message state between MUTED and UNMUTED and re-render [message-mute-button.html](message-mute-button.html) in place; `message-set-response` runs the `set-response` step (the single funnel through which likes and other responses are written) and re-renders; `message-delete` confirms and reloads the page. `with-message` scopes every one of these to a Message owned by the signed-in user, loaded from `?messageId=`.

### Browsing remote documents (browse-*)

The `browse-*` family renders live ActivityPub documents fetched from the network, not stored inbox rows. Every template starts with `.ActivityStream (.QueryParam "url")` — `build/builder_common.go` loads the URL through the server's shared ActivityStream cache with the viewer's moderation rules stamped into the document metadata, returns an empty document on failure (templates then render a "Document Not Found" card), and honors `?reveal=true` as a click-to-reveal that lifts only the viewer's own rule-hides. [browse.html](browse.html) dispatches: actors go to [browse-actor.html](browse-actor.html), everything else to [browse-tree.html](browse-tree.html). The shared [browse-header.html](browse-header.html) switches a modal between three layouts of the same URL: Nested ([browse-tree.html](browse-tree.html) — the document plus its ancestors via [browse-parent.html](browse-parent.html), with replies lazy-loaded through [browse-tree-replies.html](browse-tree-replies.html)/[browse-tree-reply.html](browse-tree-reply.html)), Index ([browse-index.html](browse-index.html) — a flat timeline of the document's conversation via `.QueryByContext`), and Code ([browse-code.html](browse-code.html) — the raw JSON-LD, pretty-printed). [browse-document.html](browse-document.html) is the card partial both layouts share. [browse-actor.html](browse-actor.html) renders a remote profile with tabs that cross into other templates — Notes opens the private `annotation` editor here, while Rule, Follow/Following, and Follows You open user-settings actions — and lazy-loads the actor's featured collection via [browse-actor-featured.html](browse-actor-featured.html). Only `browse`, `browse-actor`, and `browse-reply` open as modals; the rest are fragments swapped inside an already-open modal.

### The actor follow/mute/block buttons

[actor-button.html](actor-button.html) is the dispatcher: if `.AmFollowing url` finds a Following record it renders [actor-button-follow.html](actor-button-follow.html); otherwise `.HasRule "ACTOR" url` picks [actor-button-mute.html](actor-button-mute.html), [actor-button-block.html](actor-button-block.html), or [actor-button-none.html](actor-button-none.html) per the rule's action. State changes are separate POST actions: `actor-button-follow` runs `with-following` (which loads-or-creates the user's Following record from `?url=` or `?followingId=` — see `build/step_WithFollowing.go`), seeds `folderId`/`url` plus `behavior:"POSTS+REPLIES"` with `set-data`, saves, and re-renders the follow fragment; `actor-button-mute`/`actor-button-block` run `with-rule` (loading an existing ACTOR rule by `?ruleId=` or by match key from `?actor=`, seeding the trigger for new rules — `build/step_WithRule.go`) and save a MUTE or BLOCK rule; the `-update` variants patch `behavior`/`isPublic` or `comment` from the form; the `un*` variants delete the record and swap back to the "none" fragment, using `remove-event` to strip the automatic `closeModal` so the modal stays open. Every mutation fires `trigger-event refreshPeers`, which becomes an `HX-Trigger` response header (`build/step_AddEvent.go`); the `refreshPeers` behavior in theme-global's hyperscript then sends `refresh` to every other element carrying the same `data-peer` URL, and each one re-fetches itself through the `actor-button` action — so all copies of the button for one actor stay in sync across the page.

### Replying

The `reply` action posts a new stream into the user's own outbox: `set-args` sets the composer's `postTo` URL, then `add-stream` with `style:"inline"`, `roles:"outbox-reply"`, and `location:"outbox"` renders an inline composer on GET and creates the Stream on POST (`build/step_AddStream.go`), pre-setting `inReplyTo` to the browsed document's permalink and redirecting back into `browse-tree` so the new reply appears in the conversation.

### The hyperscript bundle

[hyperscript/listitem._hs](hyperscript/listitem._hs) defines `listItem(messageId)`, installed on every list row: when the row scrolls off the top of the viewport it POSTs `message-read` once (guarded by a `data-read` attribute) and triggers `refreshSidebar` — scroll-past-marks-read. [hyperscript/message._hs](hyperscript/message._hs) defines `message(messageId)`, installed in the message modal: it POSTs `message-read` on open and binds the window's ArrowLeft/ArrowRight keys to the Prev/Next buttons. Both files are concatenated by the `hyperscript` bundle and loaded by index.html as `/.templates/user-inbox/hyperscript`.
