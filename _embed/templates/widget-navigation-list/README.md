# Navigation List

This widget (widgetId `navigation-list`) displays a hierarchical site-navigation menu built from the current stream's position in the site map: its grandparents, parent, siblings, and children, each tier optionally shown in full or collapsed to a single entry. It is the standard sidebar navigation for content sections.

[widget.hjson](widget.hjson) defines an optional `title` plus four enum settings — `grandparents` ("All"/"Grandparent Only"), `parents` ("All"/"Parent Only"), `siblings` ("All"/"Self Only"), and `children` ("All") — where an empty value hides that tier entirely. [widget.html](widget.html) enters a chain of four named sub-templates, one per tier: [grandparents.html](grandparents.html), [parents.html](parents.html), [siblings.html](siblings.html), and [children.html](children.html) (every .html file in a widget folder is parsed into one template set, so `{{template "parents" $root}}` works across files). Each tier decides for itself whether it can render, then hands off to the next one, nesting it with indented styling under the relative it belongs to. Data comes from the Stream builder's `.Ancestors`/`.Siblings`/`.Children` query builders and `.Parent`/`.Grandparent` accessors; links use `hx-get` with the wrapper's `hx-target="main"`, `hx-swap="innerHTML"`, and `hx-push-url="true"` plus the `turboclick` class, so a new tier means adding a sub-template file and splicing it into the chain.

## Additional Information

### How the tier chain works

[widget.html](widget.html) always enters at [grandparents.html](grandparents.html), and every tier ends by invoking the next one — grandparents to parents, parents to siblings, siblings to children — with [children.html](children.html) as the terminus that invokes nothing. A tier renders its own entries only when its setting is non-empty *and* the current stream actually has the relative that tier describes; otherwise it contributes nothing and passes straight through. That is what lets intermediate tiers be skipped in any combination: with `grandparents:""`, `parents:""`, and `siblings:"All"`, the chain runs through two silent tiers and produces the sibling list, and a widget with all four settings empty renders only its optional title. Because the chain is linear rather than a dispatch, every tier below a skipped one still gets its turn.

### What each tier actually queries

Despite the name, the Stream builder's `Ancestors()` (build/builder_stream.go) does not return the full ancestor chain: it loads the current stream's parent and queries all streams sharing that parent's `parentId` — that is, the parent and its siblings, one complete peer generation. Each "All" mode therefore renders one generation's peer list, and the four tiers map cleanly onto the family tree: [grandparents.html](grandparents.html) in "All" mode builds `$parentBuilder := .Parent "view"` and lists `$parentBuilder.Ancestors.Slice` (the grandparent and the grandparent's siblings); [parents.html](parents.html) in "All" mode lists `.Ancestors.Slice` (the parent and the parent's siblings); [siblings.html](siblings.html) in "All" mode lists `.Siblings.Slice` (the current stream and its siblings); [children.html](children.html) lists `.Children.Slice`. Because each tier is a distinct generation, `"All"` on adjacent tiers never produces duplicate entries. The `"* Only"` modes collapse a tier to its single on-lineage member: "Grandparent Only" renders one link via the `.Grandparent "view"` builder, "Parent Only" one link via `.Parent "view"`, and "Self Only" just the current stream's bold label.

### Tier nesting and the lineage match

In "All" mode each template must decide which one peer in its list sits on the current stream's lineage, because that is where the next tier nests. Each file matches by hex-string ID comparison ([`StreamSummary.StreamID()`](../../../model/streamSummary.go) and the builder's `ParentID()` both return hex strings): grandparents.html compares each `$ancestor.StreamID` against `$parentBuilder.ParentID` (the grandparent's ID), parents.html compares against `.ParentID` (the parent's ID), and siblings.html compares against `.StreamID` (the current stream itself). Off-lineage peers render as plain `ellipsis`-classed links; the matching peer renders its link (or, in siblings.html, bold non-link text marking the page you are on) followed immediately by the next tier inside an indented `<div style="padding-left:8px; font-size:0.9em;">`. In "* Only" modes there is no list to search, so the next tier nests unconditionally after the single item.

### Why every tier is guarded

The settings are chosen by whoever places the widget, and nothing ties them to where the widget actually sits, so each tier has to survive being asked for a relative that does not exist. Both modes of [parents.html](parents.html) are wrapped in `.HasParent` and both modes of [grandparents.html](grandparents.html) in `.HasGrandparent`, which keeps `"All"` from listing a generation that is not really the parent generation and keeps `"Grandparent Only"` from calling `.Parent "view"` on a stream that has no parent — an error there aborts template execution, and `Stream.Widgets()` (build/builder_stream.go) only reports it and moves on, so the widget would silently render truncated.

Each tier then ends with an unconditional hand-off: if it rendered nothing to nest the next tier *under*, it invokes the next tier anyway, un-indented. This matters because a lineage match can fail even when the relative exists — `Ancestors()` and `Siblings()` both filter by permissions and publish date, so a parent the visitor cannot see, or a stream its own author is previewing before its publish date, drops out of the list that the match searches. Without the hand-off, one missing row would swallow every tier below it and the menu would end early with no error anywhere.

The builder side carries the matching guard: `Ancestors()` returns an empty query for a stream with no parent instead of falling through to the zero ObjectID, which would return the stream's *own* generation — a list no caller can tell apart from a real ancestor generation.
