# Default User Settings

The signed-in user's settings area at `/@me/settings`: account details, security, social graph, moderation rules, payments, and data portability, all in one template. [template.hjson](template.hjson) declares `templateRole: user-settings` on the `Settings` model (which operates on the User record) and is loaded directly by templateId in `build/builder_user_settings.go`, so it is not user-selectable. Every action requires `roles: ["self"]`, and [menu.html](menu.html) renders the sidebar grouping the pages into Profile, Security, Social, Payments, and Guest Profile sections.

Most pages follow a two-action pattern: a page action that renders HTML (`general`, `images`, `password`, `visibility`, `notifications`) plus a matching `*-form` action whose form is defined inline in the hjson and saved with `inline-save-button` (or `set-password` for the password form, `upload-attachments` for avatar/banner images). The larger subsystems each get an action cluster: `following*` (search, edit, delete — the follow flow that user-inbox links into), `followers*`, `rules*` (per-type editors for ACTOR/DOMAIN/TAG moderation rules via `with-rule`), `circles*` and `circle-member*` (access-control circles with product links, via `with-circle`/`with-privilege`), `merchantAccount*` and `payments` (Stripe/PayPal accounts via `with-merchant-account`), `import*`/`export*` (ActivityPub account migration via `with-import` and `with-oauth-token`), `keyPackage*` (MLS public keys for encrypted conversations, with `require-password` on delete), and `oauth` (connected clients).

The `actor-button-*` family is duplicated from the user-inbox template (follow/mute/block button fragments swapped over htmx) because the following-search modal is served from here; `actor-rule` is the modal behind the block/mute/label picker on actor pages. The `stylesheet` bundle serves [stylesheet/menu.css](stylesheet/menu.css) at `/.templates/user-settings/stylesheet`, and [resources/](resources/) holds the Stripe/PayPal logos referenced from `model/connection.go`.

## Additional Information

### How the pipelines are shaped

Three step families recur in every action, and knowing their contracts makes the whole hjson readable. The `with-*` steps (`with-following`, `with-rule`, `with-follower`, `with-circle`, `with-privilege`, `with-merchant-account`, `with-import`, `with-oauth-token`, `with-keypackage` — see `build/step_With*.go`) each load a record scoped to the authenticated user from a query parameter (`?followingId=`, `?ruleId=`/`?actor=`, `?circleId=`, `?importId=`, ...), creating a fresh record when the parameter is empty or `new`, then run their nested steps against a sub-builder bound to that record — so an inner `edit`/`save`/`delete` operates on the Following, Rule, or Circle instead of the User. `as-modal` renders its sub-steps' GET output inside the modal chrome and stops there; on POST it runs the sub-steps' POST halves and appends a `closeModal` event (`build/step_AsModal.go`) — which is why steps written after a modal's `edit` form only execute when the form is submitted. Events (`trigger-event`, `remove-event`) become `HX-Trigger` response headers: `refreshPage` and `refreshSidebar` are listened for by page wrappers, and `refreshPeers` fans out to actor-button copies (see below). The always-editable pages use `inline-save-button` (`build/step_InlineSaveButton.go`), which swaps the form's submit button for a transient "saved" state instead of navigating.

### The nine action clusters

Profile forms — `general`, `images`, `password`, `visibility`, and `notifications` each pair a page action (view-html of [general.html](general.html) etc., which embeds the form via `.View`) with a `*-form` action whose form is defined inline in [template.hjson](template.hjson). `general-form` edits name/username/email/bio/location/hashtags with a server-side username validator; `images-form` runs two `upload-attachments` steps (icon capped at 400x400, both re-encoded to webp) before saving; `password-form` posts current/new/confirm passwords into `set-password`, which verifies the current password and the server password policy server-side (`build/step_SetPassword.go`); `visibility-form` toggles `isPublic`, `isIndexable`, and the Bridgy Fed Bluesky bridge (shown only when `.UserCanBridgeToBluesky`); `notifications-form` renders [notifications-push.html](notifications-push.html) above the form so the Device Options toggle can wire the browser's Web Push subscription, which is client-side state never saved to the User record.

Social graph — `following`/`following-list` list sources with lazy loading; `following-search` and `following-search-results` power the "Follow Someone" modal that user-inbox opens; `following-edit` is both the follow flow and the editor: `with-following` loads-or-creates the record, and the form options switch labels ("Follow this Source" vs a "Stop Following" delete link) on `.IsNew`. `followers`/`followers-list` manage the other direction, with [followers-list.html](followers-list.html) rendering ActivityPub and email followers through the [follower-activitypub.html](follower-activitypub.html) and [follower-email.html](follower-email.html) partials; the `follower` detail modal ([follower.html](follower.html)) carries the same tab strip as browse-actor plus a Remove Follower button wired to `follower-delete`, and `follower-add` creates a follower by URL.

Moderation rules — [rules.html](rules.html) lists via `rules-list`; `rule-add` opens a type chooser ([rule-add.html](rule-add.html)); `rule-edit` renders [rule-edit.html](rule-edit.html), which dispatches on the rule's origin and type: ADMIN rules show the read-only [rule-edit-admin.html](rule-edit-admin.html), REMOTE rules (imported from a followed publisher) show [rule-edit-remote.html](rule-edit-remote.html) with a "Take Ownership" button that reopens the editor with `?edit=true`, and locally owned rules go to the per-type editors `rule-edit-actor`, `rule-edit-domain`, and `rule-edit-tag`. The three editors share a form shape (hidden `type`, trigger, action from the `rule-actions` provider, label shown only for LABEL actions, required summary) and carry explicit `endpoint:`/`delete:` options so the form posts back to the right URL from inside the shared modal.

Circles and privileges — `circle-add`/`circle-edit` open a three-tab form (Setup, Description, Products) where the Products tab links circle membership to purchasable products from the user's merchant accounts; `circle-members` renders [circle-members.html](circle-members.html) via `with-circle`, and members are Privilege records: `circle-member-add` (`with-privilege`) accepts a fediverse handle or email against a validation pattern, seeds `circleId` from the URL, and saves.

Payments — [payments.html](payments.html) is the hub; `merchantAccount-add` chooses a provider, then `merchantAccount-edit-stripe` (publishable + restricted API keys with `pk_`/`rk_` input patterns and a live/sandbox toggle), `merchantAccount-edit-stripe-connect`, and `merchantAccount-edit-paypal` edit the account via `with-merchant-account`; `remoteProducts` lists products fetched from the processor.

Data portability — see the import state machine below; the export side ([export.html](export.html)) lists OAuth tokens that destination servers hold via `.OAuthUserTokensForExports`, and `export-finish` (`with-oauth-token`) renders the four-checkbox "Close and Move My Account" confirmation ([export-finish.html](export-finish.html)), whose form posts to the dedicated `/@:userId/export/finish` route (`handler.PostUserExportFinish` in `server.go`) rather than back through this action; `oauth-token-delete` revokes a destination's access instead.

Encrypted messaging — [keyPackages.html](keyPackages.html) lists the MLS public keys registered by the user's devices; `keyPackage-verify` shows a fingerprint-verification modal; `keyPackage-delete` is wrapped in `require-password` (`build/step_RequirePassword.go` renders a confirm-password form and validates it on POST before the delete runs) and is a silent no-op when an administrator is masquerading as the user (`if .IsMasquerading`).

Connected apps — [oauth.html](oauth.html) lists OAuth clients holding tokens, and `oauth-token-delete` disconnects one.

Actor buttons — the `actor-button*` actions are near-copies of the user-inbox set (same `with-following`/`with-rule` pipelines, same fragment swapping, same `refreshPeers` fan-out) and exist here because the following-search modal and the browse-actor tabs point at `/@me/settings/...` URLs.

### The import state machine

`import-authenticate` opens a modal (`with-import` loads or creates the Import record) whose form collects the remote `sourceId` and a hidden `stateId` of `DO-AUTHORIZE`; on save, the Import service's `calcStateChange` (`service/import.go`) resolves the transient state before the record is written: it loads the remote actor through the SSRF-guarded client, requires a Person, builds an OAuth config from the actor's advertised endpoints (pinned to the actor's own origin), and lands on `AUTHORIZING` — or `AUTHORIZATION-ERROR` with a user-facing message. The pipeline then checks `{{eq `AUTHORIZING` .Object.StateID}}` and forwards the browser to `.OAuthCodeURL` to run the OAuth handshake on the source server; a failure just closes the modal and refreshes so the error shows on [import.html](import.html). Once the callback lands the record in `AUTHORIZED`, `import-start` sets `stateId` to `DO-IMPORT`, which `calcStateChange` resolves to `IMPORTING` while queueing the background `ImportStartup` task; [import.html](import.html) re-fetches [import-progress-bar.html](import-progress-bar.html) on load and on SSE events keyed by the import ID, so progress updates live. `import-undo` sets `DO-UNDO` and then deletes: the service walks every ImportItem, calls `UndoImport` on the ones that completed, and deletes them all; `import-cancel` is a plain confirmed delete for imports that never ran. The full state vocabulary (including `DO-MOVE`/`DONE`, which run on the destination server's side of a migration) is documented in `model/import_constants.go`.

### The actor-rule save/delete conditional

`actor-rule` is the Allow/Mute/Block/Label picker opened from a remote actor's profile tab. `with-rule` loads the user's existing ACTOR rule for `?actor=` by match key, seeding the trigger on a brand-new record so a later save can resolve its canonical match key (`build/step_WithRule.go`). The modal shows a radio group of actions plus reason-code and summary fields that only appear once an action is chosen. Because `as-modal` stops after the GET render, the trailing `if` only runs on submit: a non-empty `.Object.Action` saves the rule; an empty action (the "Allow" choice) deletes the rule if it was previously saved (`{{not .Object.IsNew}}`) and does nothing for a rule that never existed. Either way `refreshPeers` fires so any visible actor buttons re-render.
