# config — Notes for AI Agents

This package defines the server-level configuration: the `Config` struct, its schemas, and the two `Storage` engines (file and MongoDB) that read it at boot and publish every later change. [README.md](README.md) covers the big rules — watcher supervision, the compare-and-swap `Write` contract, `Config.Copy()`, node-local `Source`/`Location`, and the no-`os.Exit` policy. The rules below are the finer-grained traps.

- **Adding a reference-typed field to `Config` means extending `Config.Copy()` in [config_copy.go](config_copy.go) by hand.** The copy is an explicit field list, one level deep, and no reflection test catches a forgotten field — a new map or slice left out of `Copy()` silently reintroduces the aliasing bug where a caller's "scratch copy" edits the live configuration of a running server. Extend [config_copy_test.go](config_copy_test.go) in the same change.
- **`Domain.MasterKey` and `Config.Revision` are deliberately absent from the schemas and `GetPointer` methods.** MasterKey is machine-managed AES-256 key material — generated by `NewDomain()`, validated by `DecodeMasterKey`, persisted only through storage marshaling; exposing it through `DomainSchema()` or a form would let a crafted POST overwrite live key material and orphan vault data. Revision is the concurrency counter that `Storage.Write` swaps on; a form that could set it could forge write wins. Do not "complete" the schemas with either field.
- **Each storage engine has exactly ONE goroutine publishing to its `updateChannel`.** The drain-and-retry loop in `updateChannel.notify` only terminates because nothing else can refill the slot once it is drained; a second publisher breaks the never-blocks guarantee the watchers depend on.
- **The watcher loops must not gain any exit path besides `Close()`.** Both sources die quietly — the change stream ends with `Next()` false and `Err()` nil when the server closes it, and an fsnotify watch detaches on every atomic-rename save — and an unsupervised loop leaves the node running a frozen configuration with nothing in the log. Companion invariants inside [storage_mongo.go](storage_mongo.go): resume with `SetStartAfter` (never `SetResumeAfter` — only StartAfter can pick up after an `invalidate`), drop a rejected resume token rather than retrying it, and re-read the configuration on every reopen to cover missed events.
- **Callers of `Storage.Write` keep the RETURNED config, not the one they passed in.** `Write` stamps `Revision+1` into the stored document, so saving again from the input value conflicts against your own write. This bites test helpers too: read the current revision first, or thread the returned value forward.
- **Pass a POINTER when validating against these schemas.** The `GetPointer` methods are declared on pointer receivers, so `schema.Validate(&smtp)` resolves properties and `schema.Validate(smtp)` fails every one of them. `SMTPConnection.Validate` carries the RULE comment.
- **`--db`/`EMISSARY_CONFIG_DB` beats the database named in the mongo URI path, which beats `emissary`.** `resolveConfigDatabase` in [commandline.go](commandline.go) implements this precedence; a new source of the database name must respect the `isExplicit` distinction, or cluster nodes with mixed flags end up watching different collections and never see each other's changes.
- **The config file is written mode 0600, and half-written files are skipped, not applied.** It carries secrets (SMTP passwords, connect strings, master keys), and editors fire several events per save, so `FileStorage.reload` deliberately discards an empty or unparseable read and waits for the settled contents.
- **Reads are pinned to `primary` + `majority`, and `load` sorts by `_id`.** A connect string carrying `readPreference=secondary` would otherwise reload a stale configuration with no second change event coming, and an unsorted `FindOne` lets nodes pick different documents when the collection somehow holds more than one.
